## 3. Сводка: что из стандартного есть в журналах, чего нет

**Покрыто сценами S1–S12** (снизу вверх): A1–A3, B1 (частично), B4, C1, D1, D3, D4, E1, E2, F1 (как момент), F2, F3, F5, G1, G2, H1–H4.

**Кандидаты в сцены-[гипотезы]** (в журналах нет, в каталоге есть — нужны продукту для других людей):
- **S13 Новое приложение с нуля** (B2): пустая папка → каркас → первый запуск. У пользователя всё начиналось внутри существующих папок; «сделай самое простое приложение» (HARNESS, 13.09) — ближайший след.
- **S14 Инцидент / сбой продукта** (C2, C3): срочная починка ночью, CI упал, конфликт слияния. Отличается от S7 (сбой харнесса) тем, что горит чужое.
- **S15 Миграция / крупное обновление** (D2): многодневная работа с известным объёмом — единственный сценарий, где честен «шаг N из M» и прогноз времени (state-visibility C1–C3).
- **S16 Работа не с рабочего компьютера** (F4, G1 «даже когда компьютер выключен»): назначить, посмотреть состояние, ответить на вопрос агента с телефона/из GitHub. У пользователя — Telegram-канал и «ты здесь?» издалека, но без экранов.
- Не из каталога, но из логики продукта для других людей [обобщение]: **онбординг нового человека в существующий проект с агентами** (A1 для человека, а не для агента) и **двое людей в одном проекте** (Copilot: `@copilot` в PR, комментарии — коллективные поверхности). Вендоры это не описывают как сценарий агента; в фазе 2 — решить, нужны ли они как сцены или как персоны в S4.

**Что каталог говорит о границах** (полезно для критериев провала): Copilot — сессия ≤ 59 мин, одна ветка, один PR; Anthropic — расписание «не может задавать уточняющих вопросов» → критерий успеха и адрес результата задаются заранее; S5 — не делать агента там, где хватает одного вызова.

- Codex: только главная; раздел use-cases не открыт. Devin/Factory/Warp/Replit/Windsurf — не в этом проходе.
- Каталог — про «что делают», не про «как показывают состояние»; последнее — в `products.md` и `state-visibility.md`.
