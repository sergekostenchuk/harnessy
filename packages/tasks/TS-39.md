## Факты движка (сверено 26.10, №2016)
- Журнал: `task` от владельца/оркестратора; на `task` место отвечает автоматическим `status` (для записей от owner/harness `status` не создаётся — after-turn.ts:7); `ack` — служебное подтверждение доставки владельцем, НЕ исход; `verdict` отвечает на `review-request`, не на task. `pendingFor(seat)` — недоставленные; `/api/swarm` вычитает из них `turn.records`; курсор доставки двигается и при восстановлении. Состояния мест: unsent/uncertain/recovering, прерывание, пропуск (TS-07/26).
- Состав: `/api/assign` — только оркестратор из чата без роли (rooms.ts:61, иначе `proposal_required`); остальные роли — только через предложение (`propose` из контекста оркестратора) + `/api/seats/confirm` + `/api/seats/owner`. Инструкция роли читается `/api/project/file` без hash; записи нет. Отзыв 38.4 узнаёт только ответы автопилота и пары `promotion:<op>:intro/task` (journal.ts:84).

## 39.1 — Очередь задач (потребитель: блок «Очередь» на полотне работы и экран «Команда агентов · очередь»)
Хранилище: `state/tasks.ndjson` (append-only, формы свои): события `created {n, taskId, text, ts, by}`, `assigned {taskId, to, seq (запись task в журнале), ts}`, `revoked {taskId, seq, reason}`, `closed {taskId, outcome, bySeq}`. Номер `n` — порядковый при создании, не меняется при переназначении; `taskId` — хэш(project instance, n, created ts). Задачи, назначенные до 39 обычными записями `task` от владельца, в реестр не попадают (нет ретро-нумерации; показываются отдельной группой «вне очереди» по seq, без номера, только чтение).

| № | Что видит человек | Исход «готово» |
|---|---|---|
| 1 | `POST /api/tasks {text, to?, project, instance}` — создать задачу (owner-only); с `to` — сразу запись `task` в журнал адресату с `thread:'task:<taskId>'` и событие `assigned`; без `to` (решение 2) — только `created`. Действие владельца = «возвращение владельца» для автопилота «до ответа» (TS-38 п.3) — через тот же `ownerAutopilotAction`. | Тесты: с адресатом (запись в журнале, pendingFor содержит); без адресата; подделка instance → `project_changed`; повтор с тем же idempotency-ключом (хэш текста+ts клиента) не создаёт второй задачи. |
| 2 | `POST /api/tasks/:taskId/assign {to, project, instance, expectedState}` — назначить/переназначить: под project-lock проверка текущего состояния по реестру и журналу (в работе — отказ `task_active`; адресат удалён — `seat_unknown`); новая запись `task` тому же `thread`; прежняя запись отзывается долговечным маркером `harness rejected origin:'task-reassign' reply_to:<seq>` — `pendingFor` исключает отозванные (обобщение фильтра 38.4 на этот origin), после рестарта тоже; оба адресата не получают одну задачу. Клавиатурный путь: меню «Назначить» в строке задачи (не только перетаскивание). | Тесты: из очереди → новому; активная → отказ; двойное назначение (гонка) → одна запись; рестарт между маркером и доставкой; прежний адресат с уже начатым ходом не прерывается (отзыв только недоставленного). |
| 3 | `GET /api/tasks` (owner и места с `read_pane`-правом на владельца; иначе 403) — список: `n, taskId, text, to, state, reason, thread, assignedSeq, ts, replies`. Состояние по доказательствам, без чтения текста: **в очереди** — назначена и `assignedSeq` ∈ `pendingFor(to)` и не в `turn.records`; **в работе** — доставлена (seq < курсора адресата или ∈ `turn.records`) и нет закрывающего ответа; **на ревью** — есть `review-request` от адресата с `reply_to` = assignedSeq (или в том же thread от адресата); **готово** — `status` от адресата с `reply_to` = assignedSeq и типизированным `outcome:'done'`, либо `verdict` с `accepted:true` на тот review-request; **заблокирована** — `status` с `outcome:'blocked'` или `question/blocker` от адресата в thread; **без исполнителя** — не назначена; **неизвестно** — адресат удалён/unsent/uncertain/recovering, источник недоступен — с `reason`. Один `n` → одна карточка независимо от числа переназначений. | Тесты на каждое состояние из образца журнала текущего кода (один образец, без старых фикстур); переназначение не плодит карточки; состояния мест recovering/uncertain → «неизвестно» с причиной; отозванные записи не считаются. |
| 4 | Типизированный исход от места: в контракте ответа `status` поле `outcome: 'done' | 'blocked' | 'partial'` (расширение формы after-turn для ответа на `task`; старые `status` без поля = «в работе»). | Тест формы: без поля — не «готово». |
| 5 | Окно: блок очереди на полотне и экран очереди из `/api/tasks`; «＋ задача» (строка ввода, Enter); меню «Назначить» и перетаскивание на карточку роли → `assign`; фильтры по состоянию; пометки «макет» сняты; пустая очередь — «задач нет»; ошибка API — честная ошибка без макетных данных. | Снимки 1440/390 из собранного proto на своём порту; тест live-ui: нет `QUEUE0`, состояния из ответа, ошибка API → без макета. |

## 39.2 — Конструктор: инструкция роли и своя роль (потребитель: экран «Конструктор команды»)
| № | Что видит человек | Исход «готово» |
|---|---|---|
| 1 | `GET /api/project/file?…&text=1` для инструкции возвращает `hash` (sha256 байтов) — квитанция прочитанного. `POST /api/panes/:id/instruction {text, expectedHash, project, instance}` (owner-only): путь берётся ТОЛЬКО из записи места на сервере (`instructionPath` из team.yaml), не из тела; под project-lock: canonicalPath внутри проекта, не symlink наружу; hash текущих байтов = expectedHash, иначе `file_changed`; порядок — запись `note` намерения в журнал (`origin:'instruction-update'`, hash от→к) → атомарная запись файла → при сбое между ними следующий GET показывает hash и UI предлагает повторить (намерение без подтверждения не применяется). Общий файл у нескольких мест: в ответе `sharedWith:[…]`, UI предупреждает перед сохранением. ## Уточнения по сверке ревьюера №2029 (8/10, 26.10) — часть договора, обязательны
1. **Типизированный исход — до источника.** Схема инструмента места → Channel (`SendArgs`, разрешённые поля) → Record → хранение/чтение: поле `outcome:'done'|'blocked'|'partial'` у записи `status` в ответ на `task`; для задач владельца (after-turn.ts:7 пропускает owner/harness) исход сообщает адресат своим `status` с `reply_to: assignedSeq` через инструмент; текст ответа никогда не превращается в done. `partial` → состояние «частично», карточка показывает текст исхода.
2. **Состояние — к текущему назначению.** Граница доставки — `deliverySeq <= cursor` (как в pendingFor), не `seq < cursor`; курсор не доказывает работу после skip/прерывания/восстановления — приоритет фактов: закрывающий `status`/`verdict` по текущему `assignedSeq` > блокер по текущему `assignedSeq` > активный ход (turn.records содержит assignedSeq) > доставлено без ответа = «в работе» > pending = «в очереди» > состояние места unsent/uncertain/recovering = «неизвестно». Все `review-request/verdict/status/blocker` считаются только с `reply_to` = текущий `assignedSeq` (или `reply_to` на review-request этого назначения); старые ответы прежнего исполнителя в том же thread не закрывают и не блокируют нового. «Неизвестно» не разрешает переназначение (отказ `task_state_unknown`).
3. **Одно действие — восстановимо.** Устойчивый `opId` (idempotency-ключ клиента, поле `opId` в POST /api/tasks и /assign, хэш тела сохраняется рядом с ключом; другое тело под тем же ключом → `op_conflict`) до первого эффекта; порядок: событие реестра с opId → запись журнала → подтверждение; при повторе и после рестарта повтор находит уже сделанный эффект по opId и доводит недостающий шаг (task записан, assigned нет; старый отозван, новый не создан; ответ HTTP потерян). `task_active` согласуется с началом доставки очередью (проверка и отзыв — под той же блокировкой, что берёт доставка).
4. **Владельческое предложение роли.** POST /api/seats/propose: `{project, instance, opId, label, kind, vendor, model, mode, intro}`; повтор по opId возвращает тот же proposalId; классы — шесть ProposedSeat + orchestrator через `ownerSeats.kind` в createOwnerSeat с его же `role_taken` (стык сохраняется, несовместимое предложение не записывается); черновик формы хранится по проекту; смена проекта A→B→A не создаёт роль в чужом проекте (instance в теле).
5. **Инструкция.** Поле team.yaml — `instructions` (instructionPath — представление /api/swarm); GET возвращает `hash` и `sharedWith` ДО сохранения; отсутствие файла — `instruction_missing` с правом создания только для своего места; отказ `target_changed`, если между canonicalPath и записью сменилась цель/родительский symlink (повторная проверка realpath под блокировкой перед записью); успешная запись = действие владельца (отзыв «до ответа»); неуспешная сохраняет черновик.
