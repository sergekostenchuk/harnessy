## Смысл
Владелец уходит. Вопросы, которые обычно ждут его (решения `waiting`, запросы разрешений, вопросы оркестратора), в режиме Автопилота решает оркестратор:
предлагает решение, ревьюер проверяет и соглашается или возражает (консилиум через существующий канал обмена и роли проекта), при согласии решение применяется тем же
путём, каким его применил бы владелец (те же API: approve/ответ/назначение), и записывается с «почему» и составом консилиума. Утром владелец видит всё во Входящих и может
отменить. Что не входит: внешние необратимые действия (оплата, публикация, удаление данных, расходы выше условия) — всегда ждут владельца.

| № | Что видит человек | Исход «готово» |
|---|---|---|
| 1 | Включение из UI TS-36C: срок «до утра HH:MM / до ответа» и условия (что можно решать: типы решений; потолок расхода за ночь; стоп-случаи из настроек). Движок хранит состояние автопилота в настройках проекта (scope owner, с ревизией), отдаёт в `/api/status` (`autopilot: {on, until, conditions, startedAt}`), UI показывает пилюлю «◆ автопилот · до 07:00». | Тесты: включение/выключение/истечение срока; состояние переживает перезапуск; подделка из окна невозможна (только owner). |
| 2 | Пока автопилот включён, каждое решение `waiting` того типа, что разрешён условиями, обрабатывается: оркестратор получает поручение «предложи решение с обоснованием» (его место, его модель), ревьюер — «проверь предложение, согласен/возражение» (если ревьюера в команде нет — автопилот недоступен с причиной, UI TS-36C её показывает). При согласии — применение тем же API, что у владельца; при возражении — второй круг один раз, затем вопрос остаётся владельцу. | Тесты на сценарии: согласие → применено; возражение → второй круг → владельцу; тип вне условий → владельцу; потолок расхода исчерпан → стоп автопилота с записью. |
| 3 | Каждое решение автопилота — запись в журнале проекта (`state/`): что решено, почему (текст оркестратора), кто советовался (места, модели), во сколько, ссылка на исходный вопрос, стоимость консилиума; событие в поток `/api/events`. Во Входящих (TS-36B) — карточка «автопилот · решение» с «Почему», «Советовались», кнопками «Хорошо» / «Отменить». | Тесты: запись неизменяема (дописывание), событие доходит до ленты, карточка собирается из записи. |
| 4 | Отмена: если у решения есть обратное действие (снять назначение, отозвать ответ до начала исполнения, остановить запущенный ход) — выполняется тем же API; если обратного действия нет — кнопка объясняет, что именно уже произошло, и предлагает следующий шаг. Срок отмены — не придумывать: отмена возможна, пока обратное действие возможно. | Тесты на три вида: обратимое, частично, необратимое. |
| 5 | Честность и безопасность: стоп-случаи из настроек (TS-21/22) действуют и ночью; любое действие с деньгами, публикацией, удалением, сетью наружу — не автопилоту; расход консилиума учитывается в лимитах (TS-29) и виден утром. | Негативные тесты на каждый стоп-случай. |

Правила: ничего в UI не выдумывать сверх TS-36C/TS-36B — UI подключается к данным движка; формы записей — свои, на месте (решение 28.09); пять проходов;
полный `npm test`; живые модели в тестах не вызывать — заглушки мест. Задача большая: разрезать по потребителю (1 состояние → 2 консилиум → 3 журнал/лента → 4 отмена → 5 стоп-случаи),
каждый кусок — своя ветка и ревью. Сдача — SHA, таблица сценариев, вопросы.

## Уточнения по сверке ревьюера (№1851, 23.10) — часть договора, обязательны
1. **Полномочия — закрытый список.** Разрешённые операции и их параметры перечислены явно (ответ на вопрос `question/blocker/escalation`, approve/deny запроса разрешения с кодами из стоп-случаев, назначение роли из состава команды, продолжение/остановка хода места). Разрешение привязано к проекту, экземпляру вопроса, ревизии условий и хэшу точного предложения; стоп-случаи проверяются по операции и параметрам, не по описанию модели. Согласие модели — не owner-доступ.
2. **Подлинность консилиума.** Оркестратор и ревьюер — разные места проекта; ответ ревьюера принимается только от подтверждённого отправителя (место + токен), только на хэш проверяемого предложения, в пределах таймаута. Подставленный текст «согласен», старый ответ, ответ на другое предложение — ничего не разрешают. Нет ревьюера / ответ не разобран / таймаут — вопрос остаётся владельцу.
3. **Возвращение владельца и срок.** «До ответа» = первое действие владельца в этом проекте (сообщение, решение, выключение автопилота) — событие движка, не UI; «до утра» = ближайшие 07:00 в часовом поясе машины владельца (после 07:00 — следующий день). Выключение, истечение срока, изменение условий и повторное включение отзывают поколение разрешений (`generation`); проверка актуальности поколения и применение — атомарны: позднее согласие после возвращения владельца не исполняется.
4. **Однократное применение.** Устойчивый id решения = хэш(проект, вопрос, предложение, поколение); применение идемпотентно: дубли событий, повтор запроса, перезапуск между эффектом и записью журнала не повторяют эффект; повтор возвращает результат первой операции (запись намерения до эффекта, подтверждение после — как в журнале обмена).
5. **Расход и сеть.** Разрешены только вызовы моделей мест оркестратора и ревьюера в рамках потолка расхода ночи; запрещены внешние эффекты (оплата, публикация, удаление, отправка наружу, установка). Лимит считает параллельные консилиумы, второй круг и отменённые вызовы; неизвестная стоимость ≠ 0 (считается по верхней оценке модели из каталога). Исчерпание — стоп автопилота с записью.
6. **Отмена.** Привязана к конкретному применённому эффекту и его текущей версии; повторная отмена безопасна; старое «Отменить» не затрагивает новое назначение/ход. Остановка хода ≠ откат сделанных изменений; частичный исход записывается явно.
7. **Стык частей 2 и 5.** Проверка стоп-случаев и лимитов обязательна уже в части 2; отсутствие реализации проверки = отказ применения, не пропуск.
8. **Блокировки (стык 38.1/38.2, 23.10).** Отдельный канонический autopilot-lock сериализует изменение состояния, возвращение владельца, истечение и `withAutopilotGeneration(expectedGeneration, apply(snapshot))`; callback держит его, пока owner API берёт project-lock. Порядок захвата всегда autopilot-lock → project-lock, никогда наоборот (тест на порядок). Снимок `{generation, revision, conditions, stopCodes}` неизменяем; typed-отказы off/expired/generation_mismatch.
9. **Эффект автопилота ≠ возвращение владельца.** Эффекты консилиума идут через те же owner API с initiator «autopilot» (`runAutopilotOwnerEffect`): все owner-проверки сохраняются, но срабатывание «действие владельца» (гашение `until:reply`) подавлено; внешние вызовы владельца по-прежнему отзывают generation.
