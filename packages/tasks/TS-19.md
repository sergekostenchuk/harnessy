# TS-19 — Передача контекста разговора при смене вендора/модели в одном чате

Статус: факт владельца 12.10.2026 00:20 (снимки чата «Оркестратор · Юристы 4114»): после переключения gpt-6-luna → gpt-6-sol (тот же Codex) контекст сохранился; после переключения на claude-haiku-5-5 новая модель разговор не получила («предметная вводная лежит в журнале повышения, которого я не вижу»). **ВЛИТА** 11.10.2026 23:35 (ts/TS-19 9969242, codex-worker, круг 2, вердикт 9/10 №654/№657, ворота 1249/1249). Оркестратор: claude-orch.

## Причина (факты кода)
`packages/runtime/src/pane.ts:59`: при смене `vendor` → `sessionId=null`, `sessionEpoch++` — новая сессия провайдера начинается пустой; стенограмма чата (`pane.transcript`) хранится в Harnessy только для окна и в первый ход новой сессии не передаётся. Смена модели внутри вендора сессию не сбрасывает (поток Codex/сессия Claude продолжаются — контекст цел). Ручной «Передать контекст» (handoff.ts) работает между чатами, но не при переключении вендора. Принцип «модели помнят через свои сессии, ядро хранит идентификаторы» — верен, но при смене вендора нужен автоматический перенос.

| № | Что | Решение |
|---|-----|---------|
| 245 | автоперенос при смене вендора | когда у места сбрасывается сессия (смена vendor; а также потеря/истечение сессии провайдера, уже ловимая как recovering), первый ход новой сессии получает блок «Контекст этого разговора» перед сообщением владельца: вводная роли и память проекта (как сейчас) + стенограмма чата: последние N сообщений дословно (по умолчанию 12) + более ранняя часть сжато детерминированно (заголовки/первые строки сообщений, без вызова модели) в пределах бюджета токенов (по умолчанию 20 000); формат — цитируемая стенограмма с ролями и временем, чтобы модель не приняла её за инструкции |
| 246 | состояние операций | в блок входят незавершённые сущности чата: ожидающее предложение состава (proposalId/version/состав), прикреплённые документы, ожидающие подтверждения владельца, последнее поручение — из сохранённого состояния, не из текста |

| 259 | сейчас в диалоге переноса контекста при смене провайдера/модели все сообщения выделены по умолчанию — человек может по незнанию отправить всё неконтролируемо | по умолчанию НИЧЕГО не выделено; кнопка «Отправить» неактивна, пока не выбрано хотя бы одно сообщение; при нажатии «Отправить» (или «Перенести контекст») — список конкретных сообщений с чекбоксами, счётчик выбранных и объём (сообщений/символов), «Выбрать все» — отдельное явное действие, не состояние по умолчанию; выбор запоминается только в пределах одного диалога (следующий перенос снова с пустого выбора); тест: открыть диалог → ни одного выбранного, «Отправить» заблокирована; выбрать два → отправляются ровно два; «Выбрать все» → все, потом снять одно → все минус одно |
| 260 | TS-19.2 круг 1: 947200bf (ворота 1796/1796) — вердикт 7,5/10 №995: (1) P2 ПУТИ live.js:605 — вход «Передать контекст» под ответом сначала зовёт /api/handoff без текста, диалог открывается только по needSelection: при одном ответе модели весь разговор уходит без выбора (проба: журнал + один вызов модели); (2) P2 ОКНА live.js:447 — выбор хранится индексами массива SEL.items, после сдвига ленты (slice(-40) по SSE note) галочка у видимого ответа отправляет другую реплику — личное сообщение владельца; граница: /api/handoff принимает готовый text, сервер выбранное не проверяет | круг 2 (№996): (1) ВСЕ входы передачи контекста другой роли/чату открывают диалог с пустым выбором ДО любого запроса, независимо от числа ответов; (2) выбор хранится по номеру сообщения журнала (seq), не по индексу; сдвиг ленты не меняет отмеченные реплики; выбранная реплика, ушедшая из видимого окна, остаётся в счётчике; (3) `POST /api/handoff {to, chat, seqs:[...]}` — сервер сам собирает текст из журнала этого чата, проверяет, что каждый seq принадлежит чату и видим владельцу; чужой/несуществующий seq → 400 без отправки; поле text больше не принимается (МАСКАРАД); тесты: проба ревьюера /tmp/harnessy-ts19-2-independent.ts (2 падения), подмена seqs, пустой список → 400.
