## Цель
Один пакет `@harnessy/journal` с четырьмя частями и без знания об окнах, процессах и провайдерах:
- **Journal** — файл обмена `.harness/state/channel.ndjson` (только дописывание, одна запись JSON на строку, `fsync`), курсоры доставки
  `.harness/state/cursors.json`, состояние окон `.harness/state/panes.json` (чтение/запись атомарно: tmp + rename), выборки, ответы.
- **Policy** — `.harness/comms-policy.yaml`: маршруты по ролям и видам, триггеры `owner-ack` и `reply-to:<kind>`, границы раундов,
  наблюдение чужих разговоров, текст сводки для инструкций места; перечитывание по mtime.
- **Evidence** — свидетельства `.harness/evidence/<тред>/r<раунд>/report.md` по контракту Ran / Skipped / Planned / Manual.
- **Channel** — единственная точка записи для агентов и владельца: проверки формы, политика, триггеры, границы, отказы с записью
  `rejected` владельцу, состояние тредов (раунды, принято, sha, merged), ожидание подтверждения владельца (owner-ack) как состояние.
  Channel не доставляет записи окнам: он **публикует события** (`record`, `rejected`, `pendingAck`, `delivered`), на которые подпишется `runtime` (TS-04).

## Границы
Пути: `packages/journal/**`. Зависимости: разбор YAML (`yaml` — версию проверит опись); остальное — встроенные модули Node.
Роли мест и подписи Channel не знает: получает функции `roleOf(seatId) → role | null`, `labelOf(seatId) → string` и список живых мест от ядра.
Проверка SHA коммита для `review-request` — функция `resolveSha(sha) → fullSha | null` от ядра (пакет `projects`); в тестах — дублёр.
Вопрос владельцу при owner-ack задаёт `runtime` (карточка); Channel хранит состояние «ждёт подтверждения» и даёт `confirmAck(seq)` / `rejectAck(seq)`.

export const KINDS = ['task','status','question','answer','review-request','verdict','blocker','escalation','note','stop','resume','digest','proposal','decision','report'] as const;
export const SYSTEM_KINDS = ['protocol','rejected','policy','ack'] as const;
export const REPLY_KIND = { question: 'answer', task: 'status', 'review-request': 'verdict' } as const;
export interface Record_ { seq: number; id: string; ts: string; from: string; to: string[]; kind: string; thread: string | null; reply_to: number | null;
  text: string; evidence: string[]; policy: number; score?: number; round?: number; origin?: string; accepted?: boolean; bounds?: object | null;
  ack?: 'pending'; sha?: string; merged?: string; version?: number; kinds?: string[] }   // поля и имена — как в Python, байт в байт
export type JournalCode = 'kind_unknown'|'to_invalid'|'to_unknown'|'self_addressed'|'text_empty'|'text_too_long'|'reply_to_missing'|'evidence_invalid'
  |'score_invalid'|'round_invalid'|'reply_to_required'|'sha_required'|'sha_unknown'|'evidence_required'|'evidence_outside'|'evidence_missing'|'evidence_contract'|'policy_denied';
export class JournalError extends Error { code: JournalCode }
export interface Journal { lastSeq; append(fields): Record_; get(seq); read({since,limit,thread,kinds}); repliesTo(seq); pendingFor(seat); advance(seat, seq);
  markAcked(seq); savePanes(data); loadPanes(); readonly channelPath; readonly cursors }
export interface Decision { allow: boolean; pending: boolean; reason: string; route: Route | null; bounds; trigger }
export interface Policy { version; default; routes; observe; load(); maybeReload(): boolean; routeFor(from,to,kind); allowedKinds(from,to); checkSend(from,to,kind): Decision;
  canObserve(role, targetRole): boolean; summaryFor(role, seatRoles, labels): string }
export type JournalCode = JournalCode | 'ack_not_pending' | 'ack_closed' | 'write_failed' | 'initiator_invalid';
export interface Initiator { seat: string; trust: 'owner' | 'harness' | 'agent' }   // ставит ТОЛЬКО ядро; агентский ввод инициатора не содержит
export interface AgentPostInput { to: string | string[]; kind: Kind; text: string; thread?: string; reply_to?: number; evidence?: string[];
  score?: number; round?: number; sha?: string }   // ровно это и ничего больше: accepted/bounds/ack/policy/origin/merged из ввода агента не принимаются
export interface CorePostInput extends AgentPostInput { kind: Kind | 'note'; origin?: string; merged?: string }   // путь ядра (harness/owner)
export interface ThreadState { rounds: number; accepted: boolean; lastScore: number | null; sha: string | null; merged: string | null }
export interface ChannelDeps { journal: Journal; policy: Policy | null; projectDir: string; liveSeats: () => string[]; roleOf: (seat) => string | null;
  labelOf: (seat) => string; hasRepo: () => boolean; resolveSha: (sha) => string | null; mergeCommitFor: (sha) => string | null }
export type ChannelEvent =
  | { type: 'posted'; record: Record_; initiator: Initiator }            // runtime: событие `sent` отправителю, отметка явного ответа (replied)
  | { type: 'delivered'; record: Record_ }                               // РАЗРЕШЕНИЕ поставить запись в очередь адресатов (не исполнение); runtime: queued/kick, пробуждение ask
  | { type: 'pendingAck'; record: Record_ }                               // runtime: карточка владельцу
  | { type: 'rejected'; record: Record_; sender: string; reason: string } // runtime: toolError отправителю
  | { type: 'verdict'; record: Record_; thread: ThreadState };
export interface Channel {
  post(input: AgentPostInput, initiator: Initiator & { trust: 'agent' }): Record_;   // политика, триггеры, границы; отказ — JournalError (+ rejected владельцу)
  postCore(input: CorePostInput, initiator: Initiator & { trust: 'owner' | 'harness' }): Record_;   // без политики; только ядро
  confirmAck(seq: number): Record_;   // владелец (через ядро): ack-запись → delivered
  rejectAck(seq: number): Record_;    // владелец: rejected владельцу + note отправителю
  pendingAcks(): Record_[];           // ждущие решения после перезапуска
  readonly threads: ReadonlyMap<string, ThreadState>;
  on(handler: (ev: ChannelEvent) => void): () => void;
}

## Доверие и инициатор (п.1 круга 1)
Инициатора задаёт только ядро (`Initiator`); агент не может передать `from`, `trust`, служебные виды, `accepted`, `bounds`, `ack`, `policy`,
`origin: merge`, `merged`, и не имеет пути к `confirmAck`/`rejectAck`/`postCore`. `roleOf(seat) === null` → `to_unknown` (адресат) или
`initiator_invalid` (отправитель). `Journal.append` — внутренний доверенный метод Channel, в публичный интерфейс пакета для агентов не выходит.
Доверие к файлу: единственный писатель `.harness/state` — процесс ядра; `.harness/state` не входит в пути записи мест; записи `from owner`/`kind ack`
в файле считаются собственными записями ядра. Произвольно переписанный агентом файл не защищён (вне задачи; снаружи — права папки).

## Подтверждение владельца (owner-ack) — восстановимое состояние (п.2–3)
- Запись с триггером `owner-ack` ложится с `ack: 'pending'` и **не входит в `pendingFor` адресата по своему seq**.
- `confirmAck(seq)`: сначала долговечная запись `ack` (from owner, to [отправитель], reply_to = seq), затем событие `delivered`.
  **Номер доставки отделён от seq записи** (п.1 круга 2): `pendingFor(seat): DeliveryEntry[]`, где `DeliveryEntry = { record, deliverySeq }`;
  у обычной записи `deliverySeq = record.seq`, у подтверждённой — seq первой допустимой записи `ack` (A.reply_to = R.seq, R.ack === 'pending',
  seat ∈ R.to, R.from ≠ seat); список упорядочен по `deliverySeq`, в него входят записи с `deliverySeq > курсор(seat)`. Runtime после удачного
  хода вызывает `advance(seat, max deliverySeq)`; `record.seq` остаётся для `reply_to` и показа. Событие `delivered` несёт `deliverySeq`.
  Так поздняя запись не теряется за курсором и не приходит дважды — и после перезапуска (всё вычисляется из файла). Тест: смешанная очередь
  обычных и поздно подтверждённых записей, продвижение, перезапуск.
- Исходы: `seq` неизвестен → `reply_to_missing`; запись без `ack: 'pending'` → `ack_not_pending`; уже подтверждена → возвращает существующую
  `ack`-запись без новой доставки (идемпотентно); уже отклонена → `ack_closed`. `rejectAck`: `rejected` владельцу с `reply_to = seq` + `note`
  отправителю «владелец не подтвердил»; повторный reject/confirm после reject → `ack_closed`.
- `pendingAcks()` — записи с `ack: 'pending'` без `ack`/`rejected` ответа (для карточек после перезапуска).
- Вердикт с `ack: 'pending'` не меняет `threads` (ни вживую, ни при восстановлении истории) до записи `ack`.
- Поддельное `ack: 'pending'` в файле без маршрута с `owner-ack` при загрузке считается ждущим (проверить нельзя) — граница доверия выше.

## Повреждения файла и порядок записи (п.4)
- Загрузка: последняя строка без LF или не-JSON → фрагмент остаётся в файле (история не уничтожается), помечается `tailBroken`, при следующем
  `append` сначала пишется `\n`; записи с неверной структурой (нет целого `seq`, строки `from`, списка `to`, строки `kind`) пропускаются,
  число пропусков — в диагностике; `seq` продолжается от максимального валидного. Python-ядро исправлено так же (коммит в core 09.10).
- `append`/`post` — **синхронные** (`appendFileSync` + `fsyncSync`): один писатель на файл проекта — экземпляр `Journal`; событие и возврат только
  после успешного сохранения. Два процесса ядра на одной папке — вне задачи.
- **Неопределённый результат записи** (п.2 круга 2): ошибка `appendFileSync`/`fsyncSync` → `write_failed` с полем `maybeWritten: true`
  (отказ не доказывает отсутствия строки на диске); журнал переходит в состояние `recovering`: следующая операция сначала перечитывает файл
  от последнего подтверждённого смещения — найденные целые записи становятся историей (с их seq), и только затем выдаётся новый seq.
  Повторное использование seq исключено. В Python-образце воспроизведён дубль seq после ошибки fsync — не переносить. Тест: ошибка после
  фактической записи, затем продолжение и перезапуск — seq уникальны, история цела.
- Тесты: оборванный хвост, валидная последняя запись без LF, ошибка сохранения (подмена fs), сто `append` подряд — `seq` без дыр.

## Политика при повреждении (п.5)
`maybeReload` при ошибке чтения/разбора → политика помечается `broken` (прежний снимок хранится только для диагностики и `summaryFor`);
любой `post` агента → `policy_denied` «политика связи не читается» + `rejected`. Один `post` берёт **один неизменяемый снимок** политики в начале
операции, проверяет по нему всех адресатов и пишет `policy` = его версия. Восстановление файла → следующий `maybeReload` снимает `broken`.
Исторические записи по новой политике не перепроверяются. Тесты: удаление файла, битый YAML после удачной загрузки, восстановление, смена
политики между двумя `post`.

## Свидетельства (п.7) и reply_to = 0 (п.8)
Граница проекта проверяется по **реальному пути** (`fs.realpathSync`, как `Path.resolve()` в Python): `../` и символическая ссылка наружу →
`evidence_outside`; `evidence_dir(thread, round)` строится так же и проверяется. Правило verdict как в Python: каждое вложение должно
существовать (`evidence_missing`), и **хотя бы одно** — отчёт с четырьмя разделами (`evidence_contract`); остальные вложения разделов не требуют.
`reply_to = 0`: нормализация в `null` — на входе инструмента (PeerTools в ядре), а `Channel.post` с `reply_to: 0` → `reply_to_missing`
(запись `protocol` не цель); тесты на оба входа.
