## Слово владельца (сжато, без искажений)
1. Harnessy — не только для кода: команды юристов, проектировщиков здания, визуального контента — любой домен.
2. Новый проект = обычный чат без роли, с моделью и документами. Решение «создать команду» приходит из разговора (владелец или предложение модели). Оркестратор назначается в этом же чате, история и документы сохраняются; он сам пишет себе вводную из накопленного контекста.
3. Участников создаёт оркестратор: роль + вводная (кто, что делает, какой контекст). Чат участника появляется в сайдбаре только после создания. Заготовок «Исполнитель · Новый чат» быть не должно. Нажатие на чат участника — история поручений оркестратора и ответов.
4. Разделы проекта показывают материалы только выбранного проекта; пусто → объяснение («в проекте chat-test ещё не проводились исследования») и подсказка, как это появится и кто делает; «Документы проекта» вместо «Документ стадии», стадии — внутри, когда определены с командой.
5. Два журнала: «Общий журнал» внизу сайдбара (все проекты, переходы между ними, фильтр по проекту) и «Журнал проекта» внутри проекта под чатами. Ответы моделей — в журнале, связаны с запросами. Карточка запроса: проект, чат, от/кому, дата-время, текст, ссылка на ответ(ы). Карточка ответа: кто ответил (место, модель), исходный запрос, контекст и инструменты, статистика. Идея: оценка формулировки запроса и советы по промпту.
6. Логирование на время разработки: что нажали → что запустилось → что произошло → что показано; успех/отказ/сбой с причиной и местом; записи одной операции связаны; зависшее нажатие тоже видно.
7. Мастер ухода: период, заместитель, с кем советуется, число раундов, порог консенсуса; сводка перед «Подписать уход»; условия исполняет движок. Пример владельца: два раунда; оценка **выше** 8,5/10 → заместитель решает сам, иначе вопрос ждёт владельца.

## Что уже есть (факты, уточнены по №207)
- Роли и места: `team.yaml`, `/api/assign_role`, `/api/seats`, `/api/onboard` (TS-04b, TS-05). `assign_role` создаёт **другой** `chat.id` и сохраняет сессию провайдера только при совпадении `vendor`/`cwd` (`roles.ts:99`); `assignRoleAction` берёт последнюю запись владельца в пачке как поручение (`roles.ts:184`). Каталог ролей сейчас — проверяемое ограничение, не подсказка.
- `/api/handoff` — передача контекста; экраны мастера ухода в окне есть, переход к ним плохо объяснён (№9). `comms-policy` проверяет разрешённые связи, сроков/раундов/решений не исполняет.

Местный лог окна `S.log` (`live.js:15`) в движок не уходит.

## Проект решений (83–92, раунд 2)
| № | Решение | Исход |
|---|---|---|
| 83 | сайдбар проекта | источник — сохранённый жизненный цикл чатов (`chats.json` + `team.yaml`): участник виден сразу после создания, до первого ответа и сессии (`touched` — не признак создания); чаты ролей никогда не скрываются фильтром; чаты без роли — в том же списке; заготовок нет. «＋ участник» — только через сценарий 85; у владельца — «＋ чат без роли». |
| 84 | «создать команду» из чата без роли | отдельная владельческая операция «назначить оркестратора этому разговору» (имя маршрута — по описи; `assign_role` не подходит, `roles.ts:99`). Контракт: сохраняются идентичность разговора (`chat.id`), история, ссылки на документы (документы — часть сохраняемого входа операции); вводная и первое поручение добавляются ровно один раз, в том числе после частичного сбоя (маркер в чате); при совпадении `vendor`/`cwd` сессия провайдера сохраняется, при смене папки (проект создаётся по разговору) — явный перенос контекста в новую сессию с тем же разговором в окне (механизм history-transfer TS-04b); в проекте уже есть оркестратор → 409 `orchestrator_exists` с выбором «открыть существующий»; актуальность чата проверяется после каждого `await` (revision). Тесты: обычное назначение, смена папки, перезапуск посередине, повтор клика, существующий оркестратор, восстановление разговора после перезапуска до и после назначения. |
| 85 | состав команды | оркестратор предлагает команду записью `question` владельцу с сохранённым предложением `{proposalId, version, seats:[{sid, kind, label, vendor, model, mode, intro}]}`; владелец подтверждает **конкретную версию** владельческим действием (`POST /api/seats/confirm {proposalId, version}`) — произвольное «да» в чате подтверждением не является; создаёт места оркестратор ограниченным поручением через мост: `POST /api/seats` от моста принимает только `{proposalId, version}` и проверяет сохранённое подтверждение (TurnScope доказывает живой ход, подтверждение — согласие на этот состав); владельческий инициатор агенту не выдаётся; частично созданная команда продолжается идемпотентно (`seat-materialization.json`). Роли: `label` — свободное имя любого домена; полномочия только из `kind` (orchestrator/worker/reviewer/…), имя «owner»/«orchestrator» прав не даёт; `sid` — безопасный slug, генерирует движок; каталог ролей — библиотека примеров, проверка каталога в `team`/`policy`/`runtime` снимается (проверяется `kind`). |
| 86 | разделы проекта | чтение на сервере с привязкой к текущему проекту: `GET /api/project/sections/{docs|artifacts|memory|research}` — `realpath` внутри папки проекта, симлинки наружу отвергаются; «данных нет» и «ошибка чтения» — разные ответы; в ответе `project`, окно отбрасывает поздний ответ другого проекта. Пусто → текст и действие: оркестратор есть → запись владельца оркестратору («проведи ресёрч по …»); нет → предложение назначить (84), в несуществующее место ничего не шлётся. Заготовки прототипа выключены при подключённом движке. |
| 87 | «Документы проекта» | переименование пункта; стадии — разделы внутри из `docs/<стадия>/`; неизвестные стадии не подменяются прототипными. |
| 88 | журнал проекта | проекция `GET /api/journal/view` из канальных записей **и сохранённых результатов ходов**: элемент `{projectId, chatId, turnInstanceId, requestIds[], seat, model, usage, durationMs, tools[], context:{records, docs, carry}, text, ts}`; связь запрос ↔ ответ — по квитанции `runtime.recordSeqs` сохранённого результата (один ответ может относиться к нескольким запросам), не по «тому же треду после seq»; движок сохраняет в результат хода фактическую модель, список инструментов и сведения о переданном контексте (`runtime.ts:243`, рядом с `usage`); старые результаты без полей — честное отсутствие; квитанции никогда не переносятся с историей другого чата (класс TS-04b). Карточка запроса: проект, чат, от/кому, дата-время, текст, ссылки на ответы; карточка ответа: место, модель, запросы, контекст, инструменты, статистика. |
| 89 | общий журнал | список проектов — из серверного реестра (`projectRegistry`, запомненные проекты), не из тела запроса и не из списка окна; чтение журналов других проектов — только файлы, без открытия проекта в runtime и без запуска очередей; идентификатор записи составной `{project, seq}`; общий порядок — `ts`, затем проект, затем `seq`; пагинация `before={ts, project, seq}`; недоступный проект (нет папки/нечитаем) отмечается явно; переходы между проектами и работа без проекта пишутся в общий лог владельца `<projectsRoot>/.harnessy/owner-journal.ndjson`. |
| 90 | лог действий окна | `opId` создаёт окно в начале операции; `start` уходит в `POST /api/ui/log` **до** запуска действия, `end` — с исходом; проект фиксируется в `start` (записи идут в `evidence/ui-log.ndjson` того проекта, без проекта — в общий лог владельца); нет `end` → «неизвестный исход»; движок недоступен → кольцевой буфер окна (200) и доставка после восстановления связи; пределы: 2 КБ запись, ротация 5 МБ; `detail` без секретов и без текстов сообщений (идентификаторы, виды, длины); вызовы `/ui/log` сами не логируются; ошибка лога не срывает действие; в канальный журнал проекта не пишется, в «Общем журнале» — фильтр «действия окна». |
| 91 | мастер ухода | сохраняемый механизм делегирования в runtime (`comms-policy` остаётся проверкой связей): `POST /api/handoff/sign {version, period, deputy, advisors[], allowedActions[], maxRounds, rule:{minScoreAbove: 8.5}}` → `.harness/state/delegation.json` + запись `handoff` (свидетельство). Исполнение: вопрос заместителя советникам получает `questionId` и раунд; ответы учитываются только от назначенных советников для текущей версии вопроса и раунда, повтор заменяет голос, не добавляет; правило первого выпуска: минимум оценок всех советников **строго выше** порога → заместитель пишет `decision`; нет ответа/таймаут — не согласие; после `maxRounds` → `question` владельцу и ожидание; перед каждым делегированным действием проверяются срок и отзыв (`POST /api/handoff/revoke`); после перезапуска — продолжение сохранённого состояния без повтора действий; подписание не даёт прав на инструменты и слияния сверх `allowedActions`. Окно: пункт «Уйти» открывает мастер; сводка показывает именно исполняемые условия, «Подписать уход» сохраняет их. |
| 92 | оценка запроса (идея) | отложено: после 88 — подсказка в карточке запроса от модели-ассистента по действию владельца, не автоматически. |
