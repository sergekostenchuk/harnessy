## Цель
**`@harnessy/context`** — тексты и измерения, без состояния процессов:
- `onboarding(seat, how, deps)`: вводная роли дословно как `_onboarding` (где/что/когда и кем/зачем/что ожидаем/критерии/риски из `.harness/MEMORY.md`
  по заголовкам, остальное памяти ≤ 2500, модель и права, команда, политика, последние 8 записей журнала без `origin onboarding`, концовка для
  оркестратора «…чем будем заниматься?» и для прочих «жди команду»); `memorySections(projectDir)` (заглушки в скобках и прочерки не идут).
- `roleNote(seat, deps)`: инструкции роли + сводка политики + «Правки файлов тебе разрешены только в…» + «Корень проекта: …» (как `role_note`).
- `handoffPrompt(src)`, `transcriptText(transcript, limit 12000)` («Владелец/Ответ/Сосед»), `digest(viewer, others, canObserve)` как `build_digest`
  (лимиты 6000/700, заголовок «Что нового у соседних окон…», `seen` по окнам), `DIGEST_MARK`.
- `estTokens(text)`, `contextWindow(model)` по `CONTEXT_WINDOWS` (неизвестная модель → `null`), `contextCard(seat, chat, team, roleNote)` — расчёт как `api_context`
  (измерение = вход + кэш + выход последнего хода; части: вводная и инструкции · история · переданное по `HANDOFF_MARKS` · система (остаток) · свободно).

**`@harnessy/runtime`** — всё живое состояние линии, единственный пользователь `providers`, `journal`, `team`, `projects`, `context`:
- `Pane`/`Registry` как в Python (поля `settings()`/`persist()` байт в байт; `update` с правилами: во время хода ничего не менять; модель другого
  вендора переводит место к нему и сбрасывает сессию; смена cwd/сессии чистит ленту и `seen`); `Approval` — карточки владельца: `askApproval` (таймаут
  900 с = отказ), `resolveApproval` (поздний ответ → false); владелец — место `owner` без модели.
- **Шина событий**: подписчики на место и на владельца; поток `all` помечает событие именем окна (`TaggedSubscriber`); очередь 4000, переполнение
  отписывает; при подключении — сначала открытые карточки. SSE-транспорт — `api` (TS-05), здесь — источник и формат событий (`delta`, `tool`, `toolError`,
  `approval`, `approvalResolved`, `done`, `error {message, sessionId}`, `note`, `state`, `sent`, `queued {record, pending}`, `owner {record}`, `delivered`, `peerReply`).
- **Очередь и доставка**: `kick(seat)`/`pump`: пока место свободно и не `halted` — `DeliveryEntry[]` из журнала; `stop`-записи не ход; реплики в ленту
  (`me` для владельца, `peer` «[от <подпись>] …»), `renderInbox` (одна запись владельца task/note/question — текст как есть, иначе «Входящие записи: N» +
  «Как отвечать: …» дословно), `provider.runTurn` через `TurnContext`; успех → `advance(seat, max deliverySeq)`; отказ → лента откатывается, записи
  остаются в очереди, события `error` и `note «N записей остались в очереди…»` (урок 08.10: окно не должно зависнуть).
- **Ход** (`runTurn` ядра): `busy`, `touched`, снимок, `digest` + `carry` («Прежний разговор (был без папки, продолжается здесь)…», «в сообщение добавлена
  сводка соседей (N символов)»), запись ответа `ai`, `afterTurn`; `TurnContext` собирается здесь: `publish`, `askApproval`, `session` (сохранить сразу),
  `setHandle`, `signal` (отмена = `interrupt`/`halt`/`reset`), `env = projects.proxyEnv(vendor)`, `roleNote`, `peers`, `tools` (PeerTools, связанные с местом
  и ходом, `from` не из аргументов), `relayDepth`, `projectDir`, `writableRoots`, `registerProcessToken`/`revokeProcessToken` (реестр токенов места для `api`).
- **После хода** (`afterTurn`): автоответ на `question`/`task` от не-владельца, если нет явного ответа (`replied`), с `origin auto`; `review-request` без
  вердикта → `awaiting`; напоминание «Вердикт на review-request #N не получен…» (`origin nudge`), второй раз → `escalation` владельцу и автору.
- **`ask`** между окнами: `question` с `origin ask`, ожидание ответа ≤ 1800 с по `reply_to`, глубина ≤ 3, запрет встречного вопроса, `peerReply` источнику.
- **Чаты мест** `.harness/state/chats.json` как Python (`id c<hex мс><2 байта>`, `title` из первой реплики владельца или «вводная роли», `active`
  по месту; у роли один активный чат — прежний закрывается с переносом контекста текстом/выжимкой (выжимка — ход модели с текстом запроса дословно)/без;
  у «без роли» чаты параллельные; `chats_open` возвращает чат активным).
- **Разговор без роли** (`room`): `makeRoom` (чат/чтение, сохранение сессии при той же модели), `roomSet`, `roomMove` (переезд с переносом текста, `create`
  через `projects.initProject`), `assignRole` (перенос разговора в существующее место с закрытием его чата или новое место; без проекта — только
  оркестратор, проект из разговора в `projectsRoot`; статус «Назначена роль …» в журнал; вводная; `kick`).
- **Назначение роли как действие** (`createSeat`): каталог, «сначала оркестратор», занятость одиночной роли, `team.addSeat`, место, чат, запись `status`
  (`origin assign`) с инициатором, вводная (`origin onboarding`), `kick`; `onboard` — вводная один раз при первом открытии чата (`_onboarded` по журналу).
  Инструмент `assign_role` оркестратора и путь владельца принимают необязательную специализацию `{title, text}` (аннотация владельца №1): роль из
  каталога даёт права, текст специализации уходит в `roles/<sid>.md` через `team.addSeat`, вводная включает его как «Что делаешь».
- **Передача контекста** (`handoff`): правила 08.10 (пустой источник — отказ; ≤ 1 ответа — весь разговор с типовым промптом; ≥ 2 — `needSelection`; одна
  запись всем адресатам `origin handoff`; в источник — «[от харнесс] контекст передан: …»), лимит 60 000.
- **Стоп**: `interrupt` — сначала отклонить карточки места, потом `handle.interrupt()`; `halt` (`.harness/state/halt.json`) — прервать идущие,
  новые не начинать, записи ждут; снять может только владелец; `steer` — запись `note origin steer` + `handle.steer`.
- **Подтверждение владельца** (owner-ack): по событию `pendingAck` карточка владельцу («Подтвердить отправку #N …?», 86400 с) → `confirmAck`/`rejectAck`.
- **Слияние** (`merge`): роль ∈ `mergeRoles` + owner, свой git, SHA с принятым вердиктом, `gitops.mergeInto`, запись `status origin merge` с `sha`/`merged`.
- **Сообщение владельца** (`chat`): `OWNER_KINDS`, тред `T<seq>` у task, `needDirect` для не-оркестратора при наличии оркестратора, `stop` прерывает ход.
- **Открытие проекта**: оркестровка `team.loadTeam` → `policy` → `journal`/`Channel` → `Registry` → `projects.openProjectGit` → восстановление мест
  (`panes.json`: вендор/модель/режим/сессия/digest), чаты, `halt`, треды (через Channel), `rememberProject`; при смене проекта — отмена насосов и `providers.close()`.
- **Токены мостов**: реестр «место → живые токены»; `validateBridge(seatId, token)` = токен зарегистрирован И у места идёт ход (для `api`).

## Границы
Пути: `packages/runtime/**`, `packages/context/**`. Зависимости: только пакеты `@harnessy/*` и встроенные модули. HTTP, SSE-транспорт, статика — `api` (TS-05).
Провайдеры в тестах — дублёры (`FakeProvider` из `test_roles.py`: `run_turn` пишет `done` и возвращает «готов: <id>»); git — настоящий на временных папках.

| 38 | неполное состояние (п.9) | нет провайдера вендора → отказ хода `no_provider`, событие `error`, записи остаются в очереди; сохранённая сессия недоступна (`session_missing`) → runtime снимает `sessionId`, пишет `note` «сессия модели не найдена — начат новый разговор» и повторяет ход один раз без `resume`; место активного чата удалено → запись чата остаётся, `active` чистится при загрузке; `chats.json`/`halt.json` повреждены → значения по умолчанию + `lineErrors`; частичное назначение (team записан, chat/status/onboarding нет) → общий `ensureSeatMaterialized(sid)` для всех четырёх путей создания: место из team, чат если нет, записи `status origin assign` и вводная если нет (по журналу) — повтор не создаёт дубль и не теряет вводную |
| 39 | `context` — чистые функции | `memorySections(text)` получает текст (файл читает runtime); `digest(viewer, others, canObserve)` → `{text, nextSeen}`; всё остальное — данные на входе (память, инструкции, команда, политика, история, время) |

## Граф подзадач
```
context: A тексты (onboarding/roleNote/handoff/transcript/digest) → B измерения (estTokens/contextWindow/contextCard)
runtime: C Pane/Registry/Approval/шина → D очередь и ход (pump/runTurn/afterTurn/ask, TurnContext, токены) → E чаты + комната + назначение + вводная
         → F handoff/halt/interrupt/steer/approve/chat → G открытие проекта и восстановление → H merge
Опись (до всего): все точные тексты (как в TS-02), поля settings()/persist()/chats.json байт в байт, список событий и их полей.
```

## Сдача и приёмка
`npm test` зелёный; таблица «строка → тест»; `panes.json`/`chats.json`/`halt.json` совместимы с Python-ядром байт в байт (golden-файлы).
Вне задачи: HTTP/SSE/статика (`api`).
