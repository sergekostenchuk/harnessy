# Новое ядро Harnessy — TypeScript, модулями

Решение владельца 09.10.2026 (обсуждение с ревьюером Codex, чат REVIEW-TS-NJS-Harnessy): ядро пишется заново на TypeScript/Node.js
по образцу модульной сборки DSH (`packages/` + `apps/`). Python-ядро `core/` остаётся работающим продуктом и описанием поведения
до выпуска 0.1, затем удаляется одним коммитом. Состояние до начала — тег `mvp-python`.

## Правила
1. Здесь только TypeScript. Ни строки Python, никаких импортов из `core/`.
2. Тесты живут рядом со своим кодом: `packages/<модуль>/src/**/*.test.ts` на `node:test` + `node:assert/strict` (Node 22 исполняет .ts напрямую, без сборки); `npm test` в корне гоняет все пакеты — один полный прогон на финальных байтах.
   Из `core/tests` переносятся **сценарии**, не файлы (слово владельца 09.10.2026: «тесты живут рядом со своим кодом, а не в общей папке»).
3. Форматы `.harness/` проекта (team.yaml, roles/*.md, comms-policy.yaml, state/channel.ndjson, chats.json, panes.json, MEMORY.md)
   и HTTP/SSE-контракт окна сохраняются: `ui/` и Electron не меняются при смене ядра.
4. Модуль не лезет в чужую зону: провайдер не управляет командой, конструктор не исполняет, сеть не знает о разговорах, VPS не трогает чаты.
5. Стабильные идентификаторы и события с первого коммита (seq записи, id места, id чата, id хода): аналитика читает их позже.
6. Нет заглушек «на будущее»: пакет появляется вместе с рабочим кодом и тестами.
7. Проверки проверок запрещены, тесты ради тестов запрещены (слово владельца 09.10.2026). Тест — только на сценарий поведения продукта
   или на класс дефекта, который уже ловили; у каждой проверки названы риск и ожидаемый результат. Пишем код.

## Окно и дизайн-код — остаются из Python-версии (слово владельца 09.10.2026)
`ui/` не переписывается: сборка `ui/deploy` (proto.css, proto.js, live.js, cx.js, ctx.js, set.js, conn.js, дизайн-код графит + коньяк),
эскизы `ui/sketches`, оболочка `ui/desktop` (Electron, preload с выбором папки). Новое ядро обязано отдавать ту же статику
(`/sketches`, без кэша, версии ресурсов) и тот же HTTP/SSE-контракт (`/api/status`, `/api/chat`, `/api/events`, `/api/handoff`,
`/api/assign`, `/api/seats`, `/api/projects`, `/api/room/move`, `/api/context`, `/api/settings`, `/api/connections`, `/api/halt`,
`/api/interrupt` и остальные из `core/app/server.py`), чтобы окно и Electron не заметили смены ядра.

## Хранение — файлы проекта, не база (принцип с первого коммита)
Состояние проекта живёт в его папке `.harness/`, как в Python-ядре, те же форматы:
- `team.yaml` и `roles/*.md` — команда и инструкции ролей; `comms-policy.yaml` — кто кому может писать;
- `state/channel.ndjson` — файл обмена: журнал записей «кто, кому, что, по какому поручению», только дописывание, с курсорами доставки по местам;
- `state/chats.json` — чаты по местам с полным текстом; `state/panes.json` — настройки мест и их сессии у провайдеров;
- `MEMORY.md` — память проекта (цель, ожидания, критерии, риски, решения, уроки), читается во вводные ролей;
- `evidence/` — отчёты прогонов и свидетельства к вехам.
Сами модели помнят через свои сессии (Claude, Codex); ядро хранит только их идентификаторы. Настройки владельца — `~/.harness-*.json`.

## Канал и роли
Обмен — `~/.harnessy-review/channel.ndjson` (отдельный от OMG; README и вводные рядом). Оркестратор `claude-orch` (Claude Code), ревьюер

воркер работает в `~/harnessy-wt/<id>` на ветке `ts/<id>`, вливает оркестратор после полного прогона и вердикта.

## Главный сценарий первого запуска (слово владельца 09.10.2026 ~02:40)
Harnessy должен воспроизвести нашу командную работу этой ночи: оркестратор в окне ставит задачу воркеру (запись `task` с тредом и таблицей исходов),
воркер отвечает описью (`answer`), получает договор (`decision`), сдаёт `review-request` с SHA, ревьюер даёт `verdict` с баллом и раундом по `bounds`
политики, при исчерпании раундов — `escalation` владельцу, принятый SHA сливает оркестратор инструментом `merge`; владелец видит всё в чате и журнале,
роли просыпаются по событию (курсор доставки), а не по таймеру. Это пятый, главный сценарий приёмки 0.1. Форма задачи (таблица, граф, фазы
опись → договор → код, отчёт прогона как свидетельство) — в инструкциях ролей и библиотеке 0.3, ядро для неё уже есть.

Порядок внутри 0.1: `providers` → `runtime` + `journal` → `team` + `context` + `projects` → `api`.
Первая задача — адаптеры: единственная настоящая неопределённость переноса.
