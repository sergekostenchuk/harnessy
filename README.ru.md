# Harnessy

Окно владельца над командой ИИ-агентов: роли (места) со своими инструкциями, общий журнал обмена с курсорами доставки, политика обмена, передача контекста между агентами и право вето владельца на всё, что имеет последствия. Один репозиторий, три части:

- **`packages/`** — новое ядро на TypeScript (Node 22, строгий TS, тесты рядом с кодом): влиты `providers`, `journal`, `team`, `projects`, `context`, `runtime`; следующий — `api`. Правила и карта модулей — `packages/README.md`.
- **`core/`** — Python-движок (aiohttp, `127.0.0.1:3777`): сегодня на нём работает продукт, и до выпуска 0.1 он служит описанием поведения; после перехода удаляется одним коммитом (тег `mvp-python` — состояние до переписывания).
- **`ui/`** — окно: дизайн-код и эскизы экранов (`ui/sketches/disarto`), прототип с рабочим слоем (`ui/deploy`), оболочка Electron (`ui/desktop`). Окно не переписывается: ядро обязано отдавать тот же HTTP/SSE-контракт.

English version: [README.md](README.md).

## Запуск (сегодня)

```bash
~/Harnessy/core/run.sh          # движок на 127.0.0.1:3777 (нужны `claude login` и вход Codex)
~/Harnessy/ui/desktop/run.sh    # окно Electron; если порт молчит, оно само поднимает движок
npm test                        # новое ядро: строгая сборка всех пакетов + тесты (376 на 09.10.2026)
```

## Шесть вопросов об архитектуре

Пометки: **[код]** — влито в `main` и покрыто тестами; **[договор]** — согласовано в `packages/tasks/TS-0N.md`, реализация идёт.

### 1. Один ли источник истины у состояния проекта?

**Да: папка проекта.** Всё о проекте лежит в `<проект>/.harness/` обычными файлами, одни и те же форматы у Python-движка и нового ядра **[код]**:

| файл | что хранит |
|---|---|
| `team.yaml`, `roles/*.md` | места, их вендор/модель/режим, инструкции ролей и специализации |
| `comms-policy.yaml` | кто кому может писать, какие виды записей, триггеры, кто кого наблюдает |
| `state/channel.ndjson` | журнал обмена: только дописывание, первая запись — протокол, `fsync` на каждую запись |
| `state/cursors.json` | курсоры доставки по местам (что каждое место уже получило) |
| `state/chats.json`, `state/panes.json` | чаты с полным текстом; сессии и настройки мест у провайдеров |
| `state/halt.json`, `state/attempts.json`, `state/seat-materialization.json`, `state/ack-events.json` | выключатель владельца и долговечные квитанции незавершённых операций (см. 2) |
| `MEMORY.md`, `evidence/` | память проекта, читаемая во вводные ролей; отчёты ревью и прогонов |

Память процесса — кэш этих файлов: при каждом открытии проекта движок восстанавливает из них места, чаты, курсоры, ожидающие подтверждения владельца и незавершённые операции. Модели помнят через свои сессии у провайдеров; ядро хранит только их идентификаторы. Настройки владельца (параметры, закреплённое, известные проекты, маршруты подключений) — в `~/.harness-*.json`, вне проектов. Базы данных нет.

### 2. Как сохраняются и восстанавливаются незавершённые операции?

**Долговечное намерение до эффекта, долговечная квитанция после него, «неопределённо» — полноценное состояние** **[код]** для ходов и назначений ролей, **[договор]** для подтверждений владельца и слияний (TS-04c):

- **Ход модели.** До вызова провайдера движок пишет *попытку* (`attempts.json`: id хода, доставленные записи журнала, время старта). После ответа провайдера ответ записывается в чат как запись результата с `deliverySeq` и квитанцией (`runtime: {turnInstanceId, recordSeqs, effectsPending, interrupted, nextSeen}`), затем продвигается курсор журнала, затем выполняются эффекты после хода, затем сохраняется место — и только после этого квитанция помечается завершённой. При открытии движок доводит оборванный этап **без повторного вызова модели**.
- **Отказ после того, как модель могла подействовать** (обрыв транспорта, падение процесса, закрытие проекта) оставляет попытку в состоянии `uncertain`: курсор не продвигается, автоматическая доставка месту заблокирована, владелец видит заметку, и только его следующее действие к этому месту снимает блок. Два перезапуска подряд или запись другого агента модель не запускают.
- **Назначение роли** — запись операции (`seat-materialization.json`) до первого эффекта с полным нормализованным входом (роль, вендор, модель, режим, специализация, выбранные инструкции, ожидаемый файл места) и отметками этапов (команда, файл места, чат, статус, вводная). Повтор доводит только недостающие этапы, принимает только свой файл места, не дублирует вводную и не угадывает инициатора.
- **Подтверждения владельца и слияния (TS-04c, договор).** Намерение слияния (исходный HEAD, полный SHA, ветка, выбранный вердикт, инициатор) пишется под git-блокировкой до первого изменения git; после перезапуска оно сверяется с git: доказанное слияние получает результат и статус, неоднозначное становится типизированным неопределённым состоянием без автоматического повторного слияния. Записанное решение владельца по карточке доводится как записанное, а не выбирается заново.
- Сбои записи журнала восстановимы: оборванная последняя строка не склеивает следующую запись, а решения владельца публикуются через `ack-events.json`, чтобы повтор не доставил дважды.

### 3. Где проходят границы полномочий агента?

- **Политика** (`comms-policy.yaml`): маршруты задают, какое место какие виды записей может слать кому; `observe` — чьи чаты роль может читать; записи, требующие подтверждения владельца, ждут с `ack: pending`, пока владелец не разрешит или не отклонит **[код]**.
- **Срок полномочий хода** **[код]**: каждый ход получает неизменяемый `TurnScope {projectDir, seatId, turnInstanceId}`; инструменты агента замкнуты на него и отвечают `turn_ended`, как только ход завершён, отменён или проект сменился. Отправитель никогда не берётся из аргументов инструмента.
- **Токены процессов** **[код]**: процесс Codex получает секрет процесса; HTTP-мост сопоставляет токен → место → активный scope и отвергает чужие и отозванные токены (`token_invalid`) и простаивающие процессы (`turn_ended`); scope перепроверяется непосредственно перед каждым защищённым эффектом, после всех ожиданий.
- **Поручение** **[код]**: оркестратор может создать место только в ходе, начатом записью самого владельца, взятой из неизменяемого снимка записей хода.
- **Права и файлы** **[код]**: режим места (chat / read / check / web / ask / edit / all) переводится в канонический набор прав провайдера; писать можно только в корень проекта или свой worktree; рискованные действия поднимают карточку подтверждения владельцу.
- **Слияние** **[код]/[договор]**: только роли из `mergeRoles` и владелец, только SHA с принятым вердиктом, только на интеграционной ветке с чистым деревом.
- **Выключатель владельца** **[код]**: `halt` прерывает идущие ходы и держит все очереди; снять его может только владелец.

### 4. Как отделены действия с внешними последствиями от генерации текста?

Модель производит текст и события; мир она не трогает напрямую.

- **Только через ядро.** Отправка другому месту, вопрос ему, чтение его чата, назначение роли и слияние существуют только как инструменты, которые реализует ядро (`PeerTools` → `RuntimeActions`). Каждый проходит проверки политики журнала и ворота подтверждения владельца и перепроверяет scope хода непосредственно перед эффектом **[код]** (слияние и вопрос появляются с TS-04c **[договор]**).
- **Эффекты на стороне провайдера** (правки, команды) ограничены режимом прав и песочницей провайдера, выбранными по режиму места, корнями записи и карточками подтверждения, на которые владелец отвечает в окне **[код]**.
- **Квитанции, а не повторы.** Внешние действия не идемпотентны, поэтому ядро никогда не перезапускает ход с неизвестным исходом (см. 2). Полученный результат, у которого упал локальный учёт, сохраняется и доводится; результат, который «мог случиться», оставляется владельцу.
- **Передача несёт только текст.** При переезде разговора между местами или проектами переносятся текст и его метаданные; квитанции выполнения остаются у места, которое их произвело **[код]**.

### 5. Можно ли заменять провайдера без изменения runtime?

**Да.** Runtime зависит от одного интерфейса — `Provider` в `@harnessy/providers`: `runTurn(seat, message, ctx)`, `listSessions`, `sessionMessages`, `auth`, `models`, `reset`, `close`, с `TurnContext`, который даёт runtime (сигнал отмены, публикация событий, карточки подтверждения, обратные вызовы сессии и handle, окружение прокси, заметка роли, соседи, инструменты, реестр токенов процессов, корни записи, `modelStarted`). Реализаций две — Claude через Agent SDK и Codex через JSON-RPC его app-server, — а собственные тесты runtime идут на дублёре провайдера через тот же интерфейс. Провайдеры подставляются как `RuntimeDeps.providers[vendor]` **[код]**. Другие модели (Qwen, DeepSeek, GLM, Kimi, Ollama) уже доходят до мест через локальный роутер провайдеров Codex без изменений ядра. Добавить третьего полноправного вендора — реализовать интерфейс, зарегистрировать его в зависимостях и расширить объединение `Vendor` и каталог моделей; логика хода, очереди и восстановления не меняется. Запасной транспорт Codex через `@openai/codex-sdk` запланирован на 0.2 за тем же интерфейсом.

### 6. Как desktop-оболочка связана с backend и пакетами?

- **Electron — тонкая оболочка** (`ui/desktop`): `main.js` открывает `http://localhost:3777/sketches/proto/10-new-chat.html`, проверяет `/api/status`, а если порт молчит — сам запускает движок (`run.sh`) и ждёт. Рендерер работает с изоляцией контекста и без Node; единственный нативный мост — `window.harnessy.pickFolder` (preload) для выбора папки в Finder **[код]**.
- **Окно — веб-приложение**, которое отдаёт сам движок из `ui/deploy/out/site` под `/sketches`: рабочий слой (`live.js`, `cx.js`, `ctx.js`, `set.js`, `conn.js`) говорит с движком по HTTP и SSE (`/api/events`) на `127.0.0.1:3777`. Запросы защищены проверками Host/Origin/`Sec-Fetch-Site`/Content-Type, чтобы чужая страница в браузере не могла управлять движком **[код]**.
- **Backend = пакеты.** Сегодня движок — `core/` (Python). Пакет `api` (TS-05, **[договор]**) воспроизводит те же маршруты и формы JSON байт в байт поверх `runtime`, `projects` и `journal`, а `core/run.sh` становится переходником на точку входа Node — поэтому ни окно, ни Electron не меняются при смене ядра (TS-06).

## Планы: публикация проектов и подключение моделей

В Harnessy планируется встроить два инфраструктурных сервиса: **деплой** приложений на серверы и управляемое прокси-подключение к AI-провайдерам. В карте модулей (`packages/README.md`) это пакеты `network` (выпуск 0.2: сетевые маршруты, прокси/VPN, обязательность маршрута, диагностика выхода) и `infra` (выпуск 0.6: партнёры, VPS, развёртывание).

### Публикация проектов

Пользователь сможет выбрать сервер, конфигурацию и локацию, увидеть стоимость и запустить публикацию одной кнопкой. Harnessy создаст или подключит VPS, подготовит окружение, развернёт приложение, настроит адрес и HTTPS, проверит работоспособность и покажет URL. Последующие публикации будут обновлять приложение без создания нового сервера.

Рекомендуемая реализация:
- API VPS-провайдера — для создания и управления сервером.
- Coolify — как исполнительный слой публикации под собственным интерфейсом Harnessy; у него предусмотрены API и инструменты управления серверами и деплоем [1][2].
- Для MVP — один провайдер, Git-репозиторий с Dockerfile и подключение собственного аккаунта пользователя. Продажу инфраструктуры внутри Harnessy можно добавить позднее через реселлерскую программу.

### Прокси-трафик для моделей

Пользователь сможет включить прокси отдельно для выбранного AI-провайдера, указать страну выхода и установить лимит расходов. Маршрутизация будет затрагивать только нужные соединения, а не весь трафик Harnessy. (Основа уже есть: маршрут на провайдера, проверка выхода и ожидаемого IP в пакете `projects` и на экране «Подключения».)

Рекомендуемая реализация:
- Партнёрский Reseller API — для выдачи отдельных доступов пользователям, ограничения трафика и получения статистики. Такие возможности описывают DataImpulse и NSTData [3][4].
- ISP/static или residential sticky — основные варианты для тестирования; mobile — дополнительный режим по необходимости.
- Главные партнёрские ключи хранятся на backend; пользователю выдаётся ограниченный доступ.
- Перед включением проверяются выходной IP, страна и работоспособность выбранного сервиса. При сбое маршрут не переключается незаметно на прямое соединение.

### Общие принципы

Платные действия требуют явного подтверждения. Harnessy сохраняет состояние операций, показывает прогресс и ошибки, предотвращает повторную покупку ресурсов и разделяет удаление приложения и сервера.

Доступ к моделям, прокси-трафик и серверная инфраструктура учитываются отдельно. Выбор страны выхода не позиционируется как гарантия доступа к AI-сервису; совместимость и допустимость использования проверяются для каждого провайдера.
