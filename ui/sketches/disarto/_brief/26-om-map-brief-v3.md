v1 и v2 отвергнуты. Причина: рисовали внутренности машины OM и конкретный проект OMG (85 узлов, вызовы, сторож). НЕ ДЕЛАТЬ: данные OMG, вшитые числа, дашборды состояния, карту движка.

## Смысл (слова владельца — это главное)
Карта показывает, КАК ЛЮБОЙ ПРОЕКТ ФОРМИРУЕТСЯ — сайт, движок, книга, видео, сбор команды; 20 задач или 240 000 — неважно. Стадии — рамка, в которую ложится конкретный проект:
- discovery — человек излагает идею, обсуждает её с ИИ, решают: реализуемо ли, есть ли смысл. Чтобы дальше не шла «подвешенная в воздухе хуйня, которая никогда работать не будет».
- concept — для кого, что человек сможет сделать, условия приёмки.
- operation-map — первый набросок: самая верхняя схема продукта.
- specification, features.
- om-g2 (проход OM) — ПОДРОБНАЯ схема: из каких блоков, какие подблоки, как всё связано, риски. Здесь ЗАКРЫВАЮТСЯ ПРОБЕЛЫ, которые нельзя было определить раньше.
- compilation — из закрытой схемы выходит план атомарных задач: у каждой один предмет, один потребитель, один ответственный.
- execution — исполнение.
Карта — ИЕРАРХИЯ ПРОЕКТА, по которой человек может походить: видеть, как всё строится, что из чего выходит, куда идёт. Блок → подблоки → работы → задачи.

## Факты о стадиях (из кода OMG, не придумывать сверх этого)
Порядок STAGES (src/pipeline/contracts.ts): discovery, concept, operation-map, specification, features, om-g2, compilation, execution. Стадия принимается, только когда нет находок; изменилась предыдущая — следующая устаревает.
- discovery → выход: проблема, как сейчас, участники (кому польза), результаты (кто получает, что считается успехом), сценарии успеха/отказа/восстановления, ограничения, внешние системы, риски, неизвестное. Неизвестное, блокирующее стадию, не пускает дальше. Участвуют: модель-исследователь, отдельный оценщик, владелец решает.
- concept → аудитория, результат, условия приёмки; требования: каждое = польза + получатель + результат + критерии; каждый результат покрыт требованием.
- operation-map → карта L1: блоки, артефакты, связи «производитель → артефакт → потребитель», пути успеха и отказа; на каждый результат — производитель, потребители, успех, отказ, восстановление. В L1 нет кода и задач.
- specification → проверяемое поведение по каждому блоку: вход, кто, результат, успех, отказы, запрещённые последствия, состояние (кто пишет, откат, повтор), как доказать.
- features → нарезка на фичи: польза, потребитель, успех/отказ, оставшиеся вопросы.
- om-g2 → тот же граф уточняется по шагам: R0 (участники/результаты/пути из предыдущих стадий) → L1 (весь продукт) → R1 (технические вопросы: хранение, полномочия, интеграции, восстановление, тесты…) → L2 (устройство ТЕКУЩЕГО блока: подблоки и их входы/выходы) → R2 (точные ответы на пробелы) → L3 (ближайший горизонт атомарных работ с файлами и тестами; будущие задачи НЕ выдумываются) → проверка реализуемости → передача. Уточнение идёт блок за блоком («скользящий горизонт»): один блок уже раскрыт до работ, остальные пока на верхнем уровне. Пробел = вопрос к конкретному месту карты с потребителем; закрывает код, модель или владелец; отложенный пробел не теряется.
- compilation → код выводит задачи из графа без модели; ручные правки плана запрещены. Задача привязана к своему узлу карты, её входы — связи карты, выходы — её артефакты. Атомарность (решение владельца 12.09): один производитель, один артефакт, один писатель состояния, ограниченные пути записи, одна проверяемая обязанность.
- execution → по каждой задаче: реализация → проверки → независимое ревью → коммит; возвраты «нужна правка кода» / «нужна правка плана».

## ПРИМЕР (пометка «пример» на странице): «Простой харнесс с подключением двух моделей» — без наворотов, но со всеми нужными функциональными блоками
- discovery: идея — «одна модель делает, вторая проверяет, в одном окне». Проблема: сейчас два чата и ручное копирование ответа на проверку. Участник: разработчик-одиночка; внешние системы: API модели A, API модели B. Результат: ответ, проверенный второй моделью, за один ход. Риски: лимиты, разные форматы API, расход. Неизвестное: что делать, если проверяющий не согласен. Решение: реализуемо — продолжаем.
- concept: для кого — разработчик-одиночка; что сможет — подключить две модели по ключу, дать задачу, получить ответ и проверку за один ход, видеть историю и расход. Требования: Т1 подключить две модели по ключу; Т2 задача → ответ исполнителя; Т3 проверка второй моделью с вердиктом; Т4 история сохраняется; Т5 расход виден; Т6 сбой модели — понятная ошибка и повтор. Условия приёмки — по одному на требование.
- operation-map (L1), 8 блоков: Подключение моделей · Окно (ввод и показ) · Приём задачи · Ход: исполнитель → проверяющий · Вызов модели · История · Расход · Ошибки и повтор. Артефакты на связях: «подключение» (ключ + модель), «задача», «запрос», «ответ», «вердикт», «запись хода», «замер расхода», «отказ», «повтор». Путь успеха: окно → приём → ход → вызов модели (A) → ответ → вызов модели (B) → вердикт → окно + история + расход. Путь отказа: вызов модели → отказ → ошибки и повтор → ход.
- specification: у блоков — поведение, например «Ход»: вход — задача; результат — ответ + вердикт; отказ — модель не ответила за срок → ход не записывается наполовину; историю пишет только блок «История» (один писатель).
- features: Ф1 Подключение (Т1) · Ф2 Ход с проверкой (Т2, Т3) · Ф3 История (Т4) · Ф4 Расход (Т5) · Ф5 Повтор (Т6).
- om-g2: R1 ответы: история — в локальном файле базы; ключи — в связке ключей ОС; два адаптера под два API. L2 текущего блока «Вызов модели»: подблоки Адаптер A · Адаптер B · Общий формат запроса/ответа · Поток ответа · Срок и отмена. Пробелы на карте (маркеры): «как B сообщает о лимите?» → закрыл R2 по документации API; «проверяющий не согласен» → владелец решил: показать оба ответа и кнопку «переделать»; «история не влезает в контекст» → решение: брать последние N ходов. L3 — горизонт «задача → ответ исполнителя»: работы Р1 общий формат запроса · Р2 адаптер A · Р3 поток ответа в окно · Р4 запись хода в историю. Остальные блоки пока на L1/L2.
- compilation: задачи из работ горизонта, у каждой карточки: предмет (артефакт), потребитель, кто пишет, проверка. Например: «Общий формат запроса» — предмет: формат запроса; потребитель: адаптеры A и B; пишет: блок «Вызов модели»; проверка: тест на оба адаптера.
- execution: Р1 готово · Р2 готово · Р3 в работе · Р4 упала проверка → вернулась «нужна правка кода». На карте видно: что реализовано, что нет.

## ДОПОЛНЕНИЕ владельца (после запуска) — обязательно отразить
1. Атомарность шире «один производитель/артефакт/писатель» (определение владельца от 11.10): у задачи однозначный договор, ЗАКРЫТАЯ область записи вместе с тестами, которые она задевает, точные критерии, явные зависимости и весь материал для решений. Пример провала: задача формально соблюдала «один писатель», но падала на ЧУЖОМ тесте. В кадре compilation карточка задачи: предмет · потребитель · область записи (файлы + задетые тесты) · критерии · зависимости · материал. Убрать ссылку на «12.09».
2. Проход OM: работы проектирует МОДЕЛЬ, движок ПРОВЕРЯЕТ каждый её ответ — дверь атомарности (G5) с описью влияния, вопросы готовности, реализуемость (M8). Кто решает вопросы: модель отвечает на вопросы, код устанавливает факты, владелец выбирает из готовых предответов; OM идёт без владельца. Показать в кадрах om-g2: ответ модели → проверка движка (принят / возвращён с адресом), пробел → кто закрыл (код / модель / владелец выбором из предответов).
3. Исполнение: ОБРАТНЫЙ ПУТЬ. Если задача упёрлась в противоречие плана, исполнитель пишет адресную находку → задача уходит на ремонт в планировщик (карта/план чинится), а не латание кода. Затык на исполнении = дефект плана. В кадре execution: Р4 упала на чужом тесте → находка «область записи не включала задетый тест» → возврат в планировщик → задача переиздана с правильной областью.
