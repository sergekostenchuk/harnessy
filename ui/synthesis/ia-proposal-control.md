## 1. Тезис

> **Харнесс открывается не чатом, а очередью «Ждёт вас»: у каждого объекта одно слово состояния из общего для вас и агентов словаря, а чат, карта и журнал открываются как подробность строки этой очереди.**

Почему этот угол, а не «чат прежде всего» или «карта прежде всего» — по свидетельствам:
- Вопрос о состоянии — самая частая работа: ~24 % реплик Claude, 130 + 90 запросов в Codex, 20 % сообщений оркестратору, один и тот же «А где сейчас агенты?» 11 раз за 36 ч (`jtbd.md §2.1 J1`; `r2-owner-voice.md: №37, §5`); J1 присутствует во всех 16 сценах (`jtbd.md §4.1` [вывод источника]).
- Пользователь сам уже строил диспетчерскую — трижды: наблюдатель `/loop` за $425 (`claude-code.md: E8`; `r2-spend-limits.md: Э8`), 8 окон с 4 хвостами журналов (`r2-touchpoints.md: T16`), CodexLimitBar за 76 мин (`r2-spend-limits.md §3.3, Э9`); самодельные поверхности — в 5 из 20 эпизодов (`r2-touchpoints.md: N8`).
- В его собственном прототипе HARNESS «агент занят» уже убран в пользу очереди (`owner-vision.md §6 п.6`); в списке желаемых сущностей — «точка состояния места (свободен / думает / ждёт решения)», «счётчик «ждут решения»», полоса «Владельцу» (`owner-vision.md §3.4`).
- Лидеры рынка группируют по «чей ход» и выносят наверх то, что нужно человеку (`SV A1`; `products.md: A2`).
- Самый дорогой класс сбоев — невидимый простой и скрытое ожидание решения (`_system §3.4` места 1 и 3: 18,3 ч простоя канала; 9,4 ч до «заснул»).

## 2. Объектная модель

Принцип модели [вывод]: **у каждого объекта — одно слово состояния (§4), один адрес (§6.4) и один паспорт (§5)**; объекты, которые сегодня живут словами в чате (вахта, решение, делегирование, визит), становятся записями. Опора: «Решение без записи не считается принятым» (`owner-vision.md §3.2 п.18`); «Экран — проекция; истина в одном каноне» (там же, п.15); навигация по объектам, у одного объекта одинаковые виды и действия везде (R2).

### 2.2 Отношения одной схемой

```
Рабочее пространство (папка | комната)
 └─ Проект ──────────── слово состояния = худшее из компонентов
     ├─ Режим (Чат | План | Ресёрч | Команда | Наблюдение) ── переход = запись
     ├─ Стадия (… → OM-G2: R0 → L1 → … → R3 → компиляция → исполнение)
     │    └─ Задача ── Прогон (ход | R-прогон | полный прогон проверки | …) ── Артефакт
     ├─ Места (роль+вендор+модель+доступ) ── Вахты / сторожа
     ├─ Разговоры
     ├─ Бюджет; лимиты провайдеров
     ├─ Память (проект)
     └─ Очередь «Ждёт вас» ← Запросы решения (адрес → любой объект выше)
Сквозные: Визит → Рекап визита; Делегирование → стоп-случаи; Контрольная точка / инвентарь.
```

## 3. «Где я»: шесть вопросов и стоимость за секунды

### 3.1 Ответ даёт интерфейс, не агент

Правило всех экранов: на «где мы / жив ли ты» отвечает интерфейс; агенту этот вопрос не задаётся (`_critic2.md §5 п.1`). Основание: вопрос посреди хода прерывает работу (`StepInterrupted` сразу за «что происходит?» — `r2-waiting.md: F9`) и стоит 18 608 входных токенов (`codex.md: П-06`). Строка «что делает сейчас» обновляется из событий без вызова модели (у Claude Code — не чаще раза в 15 с, `SV B4`); у прототипа пользователя наблюдатель-модель стоил $425 за 137 ч — дороже воркера (`r2-spend-limits.md: Э8`).

### 3.2 Постоянные элементы экрана

### 3.3 Шесть вопросов + стоимость: где ответ на каждой глубине

| **Сколько стоит?** | % недели · возраст · сброс | расход открытого объекта по причинам (полезное / переделки / ревью / датчики); цена правильного результата | разбивка по ходам, ролям, стадиям; прогноз до сброса | `_critic2.md §5 п.7` (три требования); `owner-vision.md §3.4` «Расход и бюджет» |

- **Движение = нетерминальное состояние**; терминальные статичны; цвет меняется только при реальной смене состояния, не на каждый опрос (`SV C6`; против мигания — AP12).
- **Зелёный — только «Пройдено»**: «зелёное недопустимо без подтверждённого цикла» (`r2-screenshots.md: F1`; S26 — зелёная строка «Живое исполнение» над красной стеной кодов). Красный и жёлтый зарезервированы за срочностью (`SV D1`).
- **Каждое состояние = слово + форма + цвет**; проверка на дальтонизм и монохром (`SV H1`).
- **Состояние проекта, стадии, блока = худшее из компонентов**, причина раскрывается одним действием; «повтор запланирован» отличается от «повтора нет» (`SV A4`).
- **Слово без возраста и источника не показывается** (`_critic2.md §5 п.1`: ось «жив/ждёт/сломан» обязана иметь возраст данных и источник).
- **Не уверены — пишем «Нет сигнала», а не «Идёт»** [вывод]: пере-доверие к зелёному и к «процессы живы 2/2» при 16 ошибках лимита (`r2-touchpoints.md: T03`) дороже честного «не знаю».

Почему 12, а не ≤7 (PR 4) [вывод]: на уровне **групп очереди** их 5 (≤7 выполнено); на уровне **слов** нужны 12, потому что тип тишины (`_system §5 п.10`, 8 значений) и три исхода (`SV A3`) — разные причины с разными действиями, и при склейке возвращается «восемь причин при одном виде» (`r2-touchpoints.md: N3`).

### 4.2 Ось «процесс жив / спит / погашен»

Отдельная от слова метка в углу значка (`SV A2`):

| Значение | Метка | Смысл | Пример |
|---|---|---|---|
| **жив** | сплошная точка | процесс места работает или ждёт события | воркер в ходе; ревьюер ждёт review-request |
| **спит до HH:MM** | точка с полумесяцем + время | вахта/цикл между срабатываниями; лимит с известным прогнозом | `/loop` 10 мин; «спит до 05:10» |
| **погашен** | полая точка | процесс вышел; ответ или «возобновить» поднимут его с того же места | после перезагрузки; закрытое приложение |

Зачем: «Вахта не упала: оба процесса наблюдения живы — 2/2» при 16 ошибках лимита (`r2-touchpoints.md: T03`) — живость процесса выдавалась за исход работы; ось разводит «процесс жив» и «работа идёт» (`cjm/S11 §3 КМ-2` калибровка).

### 4.4 Очередь «Ждёт вас»

**Что попадает** (виды запроса решения, `_system §5 п.1` + `cjm/S9 §5 O6`):

| **Рекап визита** | при возврате — первый элемент очереди | нет | Advisory | см. §4.8 |

**Поля строки очереди**: вид · **адрес стадии** («OMG › R2 › блок «Знание» › D8.4e») · одной фразой что решить · **почему вы** · возраст «ждёт 1 ч 40 мин» · срок / «что будет, если не ответить» · одно главное действие (`_system НС-10`; `SV B5, E5`).

**Порядок**: (1) срочность — Warning → Caution → Advisory (`SV D1`); (2) внутри — **возраст, старейшее сверху** [вывод]: самое дорогое ожидание — невидимое долгое (9,4 ч, `r2-waiting.md: F6`; «ожидание дорого не длиной, а невидимостью причины» — вывод источника). Срочность понижается сама, когда условие снято (`SV D1`).

**Что не попадает** [вывод]: «к сведению» без действия (идёт в рекап), heartbeat и одинаковые сигналы (сворачиваются в «N однотипных с HH:MM», `cjm/S11 §5 O9`). Урок пользователя: очередь «решений владельца» 53 → 3 после разбора, 37 — шум отладочных сессий; «владельцу нужно показывать только то, что решаемо и значимо» (`owner-vision.md §8 п.1`).

**Право будить вне экрана** — закрытый список (`SV D2`; `_system НС-15`): (а) стоп-случай; (б) «Ждёт вас» с блокировкой дольше порога; (в) **Сорвалось** без запланированного повтора; (г) **Нет сигнала** у датчика; (д) необратимый шаг впереди. Присутствующему — только индикатор, отсутствующему — уведомление после задержки (`SV D3`). Порог по умолчанию — 4–5 мин (порог беспокойства пользователя в других харнессах, `r2-waiting.md: F9`) и 15 мин для заведомо долгой работы (там же) [гипотеза: для Claude Code не пересчитан, `cjm/S4 §2` МИ-2]. Канал доставки (push / Telegram / дайджест «к возвращению») — [гипотеза]: push — один след за корпус, Telegram как канал состояния — [нет свидетельств] (`_system §1.2` «Telegram»).

**След источника ответа**: каждый ответ — запись в канале «от вас» с дословным текстом, временем, каналом и видом (кнопка / текст / голос); пересказ оркестратора помечается «вывод оркестратора» отдельно; «решение» в плане без такой записи не показывается как ваше (`_critic2.md §5 п.3`; `r2-owner-voice.md 3.1-А, Б, Ж`; R18). Сегодня `from=owner` — 0 из 2 234 строк (`_system §1.1`).

### 4.6 Стоимость как часть состояния

Пользователь судит по цене правильного результата, а не по потолкам: «Если модель потратит 30 миллионов, но при этом я получу в итоге компилятор … ну так это вообще мало тогда» (`r2-owner-voice.md: №7`); потолки как регулятор отменены 21.09 (`r2-spend-limits.md §3.4–3.5`). Поэтому стоимость — не отдельная страница бюджета, а поля состояния [вывод].

| Поле | Где | Форма | Основание |
|---|---|---|---|
| **% недели по провайдеру** | строка состояния; строка места | «Codex неделя 64 % · Claude 91 %» (пример — значения 30.09 ~06:00) | `r2-spend-limits.md §3.5 п.5`; единица — % недели (`§3.2`) |
| **Возраст снимка** | рядом с каждым % | «данные 3 мин»; при недоступности — «последнее известное, 2 ч» | `SV C7`; `/usage` «Showing last-known usage» (`SV C7`) |
| **Сброс** | рядом с % | «обещано пт 23:00 · прогноз массового сброса ≈ ср 17:27, уверенность 34 %» | Reset Radar (`r2-spend-limits.md §3.3`, строка 5); несколько окон одновременно (§3.7) |
| **Темп** | быстрый просмотр проекта | «+6 % недели за последние 3 ч» [вывод] | `SV F1` (темп) |

| **Расход объекта по причинам** | быстрый просмотр задачи/прогона/места | полезное · переделки и повторы · ревью · датчики и пустые проверки | «отчитайся … чистые токены без доделок» (`r2-spend-limits.md` строка 15); 36,9 % R1–L2 — неудачные попытки (Э3); «пустые проверки» (строка 24) |

### 4.7 «Готово ставит проверка»

- Исполнитель может перевести свой объект только в **«Готово к проверке»**; **«Пройдено»** ставит событие проверки — вердикт ревьюера, код выхода полного прогона, живая проверка (`SV G5`; `_system НС-13`).
- У «Пройдено» одно действие «основание»: что проверено, чем, где, с каким результатом; раздельно pass / skip (`cjm/S5 §5 O1`; «82/82» против 79 + 3 skipped — `antigravity-chatgpt-cursor-warp.md: P2`).
- Сразу рядом с «Пройдено» — действие **«Закрепить»** (коммит / память / вики) (`_critic2.md §6 п.4`; `r2-positive.md: Н6`) и зелёная отметка (27 требований галочки — `r2-positive.md: Н14`).
- Для «решений» — симметричное правило: «ваше решение» ставит только ваша запись (`_critic2.md §5 п.10`).

### 4.8 Рекап «пока вас не было»

- Якорь — **визит** (НС-05). Пока события нет — приближение по первой реплике после паузы, помеченное «≈» (`_system §5 п.16`).
- Толкается системой при возврате как первый элемент очереди, не добывается репликой «посмотри снова» (`r2-waiting.md: F8`; `cjm/S7 §5 O1`).
- Порядок — по срочности (`SV G2`):

| Блок рекапа | Содержание | Основание |
|---|---|---|
| 1. Ждёт вас | запросы решения, возникшие за отсутствие, с возрастом | `SV G2`; R5 |
| 2. Сорвалось / нет сигнала | с зоной; внешний статус вендора, если сбой был у него | `_critic2.md §5 п.9`; 401 26.09 — 65 мин до «кодекс ожил», причину пользователь нашёл в X (`r2-touchpoints.md: T13`) |
| 3. Что живо / что потеряно | инвентарь после перезагрузки, если она была | `SV G1`; `_system ЛВ-20` |
| 4. Решения от вашего имени | по делегированию: что решено, кем, с источником; «принять / отклонить» | `cjm/S11 §3 КМ-3` контроль; «Я такого не подписывал и не говорил» (`r2-owner-voice.md 3.1-Ж`) |
| 5. Стоп-случаи | «не наступали» / «наступил X, ждёт вас» | `cjm/S16 §3 КМ-5` |
| 6. К цели или по кругу | +N влито · k возвращено (из них того же класса) · рост плана · кругов на задачу | `_critic2.md §5 п.6`; `owner-vision.md §6 п.1` (считается вручную раз в час) |
| 7. Потрачено | % недели за отсутствие; цена влитого | `_critic2.md §5 п.7` |

- Старые «Сорвалось» после долгой паузы становятся «Остановлено по выключению» и не поднимаются наверх как свежие (`SV G3`, AP9).
- Доставленное в окно отсутствия 06–13 МСК копится в дайджест «к возвращению»; ночью — как в рабочее время (`r2-waiting.md: F7`; `_critic2.md §6 п.3`).

```
 ├─ Проект → Пульт проекта (та же очередь, отфильтрованная)
 │    ├─ Стадии (полоска → карта стадий/блоков → узел)
 │    ├─ Задачи (список по «чей ход»; матрица задачи × прогоны)
 │    ├─ Места (экран команды одной таблицей строк места)
 │    ├─ Разговоры
 │    ├─ Артефакты
 │    └─ Бюджет
 ├─ Комнаты (разговоры без папки)
 └─ Датчики (вахты, сторожа, доставка, здоровье харнесса)
```

Вход в любой режим и объект — из строки (очереди, рейки, полоски стадий); глубже — быстрый просмотр, затем полный вид; «назад» всегда возвращает к Пульту с той же позицией [вывод]. Опора: R2 (навигация по объектам); `products.md: A1` (адрес «контейнер → поток»); `SV B8` (единый список агентов независимо от места запуска).

### 6.2 Постоянная полоса

Строка состояния (§3.2) не исчезает ни в одном режиме, включая полноэкранный разговор и карту; в узком окне сворачивается до трёх полей: **слово проекта · ◆ N · % недели** [вывод]. Она заменяет самодельные поверхности: 8 окон с хвостами журналов (`r2-touchpoints.md: T16`), наблюдатель (`claude-code.md: E8`), CodexLimitBar в меню-баре (`r2-spend-limits.md §3.3`) — по правилу «штатная заменяет, а не добавляется» (`_critic2.md §5 п.5`). Для меню-бара macOS — та же строка в формате CodexLimitBar (% · возраст · сброс + счётчик «ждут вас») [вывод].

### 6.3 Переходы между режимами

Переход режима — **запись**, а не реплика: кто, когда, кнопка или текст дословно, что перенесено, с каким профилем автономии (`owner-vision.md §3.2 п.18`; `products.md: B3`). Выход — одно действие в постоянном месте, которое побеждает хук (R15; `r2-transitions.md: F11`).

| Из → в | Дверь | Что фиксируется | Что переносится |
|---|---|---|---|
| Чат → **План** (M0) | см. ниже | запись «переход режима» | решения визита дословно, файлы, открытые вопросы |
| Чат → Ресёрч | «Исследовать объект» | глубина («быстрый взгляд» / «глубоко, N источников»), расход отдельно от производства | ссылка/объект; вопрос «что это · как поставить · польза мне · достоверность · коротко» (`r2-research-content.md: A1`) |
| Ресёрч → проект | «Применить к проекту …» | что из справки переносится | справка с весом (`cjm/S3 §5 O2, O8`) |
| План → Команда | шлюз стадии «Утвердить и запустить» | состав мест, множитель расхода, профиль автономии | план стадии; паспорт каждого места |
| Любой → **Наблюдение** | «Уйти» (делегирование, О12) | срок, правила, стоп-случаи, адрес дайджеста | — |
| Наблюдение → любой | возврат = визит | событие визита | рекап визита |
| Любой → Чат | «Выйти в чат» (всегда видна) | что остановлено, что сохранено | контекст разговора |

**Критический момент «чат → план» (M0)**. Сегодня — текстовая трёхходовка «оценка → готов? → выполни», растянутая до 3 ч 24 мин, без двери выхода; 0 использований встроенного Plan Mode; тревога «чтобы не потерять все идеи кода» и гнев на «несётся» (`r2-transitions.md: F2, E2, F1, F10, E4`). Как выглядит дверь [вывод, на основе `cjm/S2 §5 O1–O2` и `cjm/S1 §5 O10`]:

1. **Кнопка «В план» в композере и в строке проекта**, две ветки: **«Сразу»** и **«После обсуждения»** (слова пользователя 30.09 04:29 МСК — `r2-transitions.md: F13`).
2. **Экран условий** (R8) по рамке ГДЕ · ЧТО · ЗАЧЕМ · КОГДА · ЧТО ОЖИДАЕМ · КРИТЕРИИ · РИСКИ, предзаполненный из разговора:
   - **«Что переходит из беседы»** — список решений визита дословно, каждое с источником (реплика, время); пользователь снимает лишнее галочкой (против «какого … это не перешло сюда из дисковери?», `r2-transitions.md: E5`);
   - **«Понимание до действия»** — пересказ замысла агентом и кнопка «да, именно так» (рукопожатие «ты понимаешь, что я хочу?» — Claude 87 / Codex 564 / Hermes 12, `r2-transitions.md: F3`; `_critic2.md §5 п.2`);
   - **проверка «план для планов?»** — что на выходе первой стадии: документ или движение к коду (`r2-transitions.md: F9б`; 45 уникальных реплик);
   - **порог шлюза** (по умолчанию 9/10, правится), **профиль автономии**, **цена пути — диапазон «оценка»**, **стоп-случаи**.
3. **«Запустить»** создаёт: запись «переход режима» (кто, когда, кнопка, снимок переносимого), стадию «Дискавери» со словом «Идёт», первую строку паспорта плана (ЗАЧЕМ = подтверждённый пересказ) и, если нужно, первый запрос «Подпишите план стадии» в очереди.
4. **«Выйти в чат»** видна всё время работы плана; после нажатия — «остановлено: …; сохранено: …» (R15).

Что не делаем: система сама не толкает в план; предложение «перейти в план?» — только «к сведению», не «Ждёт вас» [вывод: пере-доверие к `/goal` + уход спать без двери выхода — `cjm/S1 §3 КМ5`].

### 6.4 Адрес объекта

Каждый объект имеет **адрес** [термин-кандидат] из двух форм [вывод]:
- **Человеческая**: `OMG › План › R2 › блок «Знание» › задача D8.4e › круг 3` — показывается в строке, в паспорте (ГДЕ) и в начале каждого сообщения о состоянии;
- **Ссылка**: `wb://omg/task/D8.4e#круг-3`, `wb://omg/decision/q-0412`, `wb://omg/seat/codex-worker`, `wb://omg/stage/R2`, `wb://room/<id>` — стабильна при переименовании; открывает быстрый просмотр объекта поверх Пульта.

Правила [вывод]:
- Адрес обязан быть **у каждой строки канала, каждого вопроса и решения** (НС-02); тема канала `OMG-CODE-<id>` сегодня даёт задачу, но не ступень (`_system §4.2` ГДЕ).
- Ссылка из чата, канала или уведомления ведёт **в быстрый просмотр**, а ответ в нём доставляется адресату с меткой «доставлено» (`SV E5`; AP8 — «продолжай» в общем разговоре не доходит до потока).
- Ссылка из Telegram или с телефона открывает **удалённый вид** только чтения с явной кнопкой «вмешаться» [гипотеза: `cjm/S16 §3 КМ-1`, `§5 O1`; сцена S16 без свидетельств].
- Ответ с удалённого устройства для стоп-случаев — только явный, без «Recommended» по умолчанию [гипотеза, `cjm/S16 §5 O6`].

## 7. Словарь терминов интерфейса

Принцип: человеческое слово первым, машинное имя — в скобках в конце (`owner-vision.md §3.2 п.19`); одно слово — один смысл (п.20); толкователь — свойство каждого сообщения, а не отдельная роль (`_critic2.md §5 п.8`). Пользователь понимает L0/L1, внутренности OM (id, ревизии, хэши) — нет (`owner-vision.md §3.5`); жаргон — 166 реплик непонимания, «Обертки, стражи, опубликовать до краха уборки. Это все абсолютно бессмысленные слова» (`jtbd.md §2.2 J4`).
