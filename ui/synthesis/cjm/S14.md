- **M14-1. ## 3. Критические моменты по PAIR (R42) [гипотеза]

Формулировки — голосом пользователя (составлены из дословных аналогов; где фраза собрана мной — помечено [вывод]). Для каждого: аудит ошибок · объяснимости · контроля · калибровки доверия.

### КМ-1. «Что именно упало и чьё это — моё, хостера или сеть? Скажи сразу, а не через час» [вывод из `codex.md П-07`, `r2-spend-limits.md Э6`, `claude-code.md P11`]

- **Ошибки:** сырая ошибка подана без зоны (401 «Incorrect API key» при подписке — `codex.md П-07`); ассистент ставит неверный диагноз и откатывает настройки (`owner-vision.md E6`; `Э6`); три исхода «не пройдено / сорвалось / нет сигнала» не различены (`state-visibility A3`).
- **Объяснимость:** зона (наша / провайдера / сеть / хостер / клиент), источник сведений (статус-страница, письмо, лог), возраст данных (`state-visibility C7`), «в каком блоке/стадии» (`_critic2.md §5 п.2`).
- **Контроль:** пользователь должен мочь переназначить зону вручную («это не ключ, это глобальный сбой»), вставить внешний сигнал (письмо, скриншот) как объект инцидента, остановить «лечение» не того.
- **Калибровка:** недо-доверие — пользователь сам ищет в X, пока ассистент лечит; пере-доверие — принять «это ключ» и перезагрузить компьютер («нужно полностью перезагрузить, видимо с компом», `claude-code.md P11`, 02:03).

### КМ-2. «Иди и разберись с сервером — но только с ним, на мак не лезь и ничего не перезаписывай» (`r2-other-harnesses.md 3.1 п.4`; `kimi-hermes-pi.md P6`; `antigravity P4`)

- **Ошибки:** агент ставит xray на Mac вместо сервера (`P6`); режет собственный канал связи, настраивая сеть (`P7`); перезаписывает файлы без версий (`antigravity P4`); «аварийный ремонт на ходу» вместо задачи (`codex.md П-09`).
- **Объяснимость:** перед каждым действием класса «запись / сеть / необратимое» — на какой системе, какой командой, что откатится, а что нет (`methods.md R14, R32`; `state-visibility E2, E7`).
- **Контроль:** границы как объект (хост, папка, ветка), а не слова в чате; стоп в одно действие с сохранением (`methods.md R15`); «превью намерения» для необратимого (`state-visibility E2`); на проде — dry-run по умолчанию (сам пользователь требовал: `antigravity E11`, §6 п.5 «read-only collectors, dry-run/proposal, реальные credentials — только с подтверждением»).
- **Калибровка:** пере-доверие — полный доступ без границ (bypass/yolo, `r2-waiting.md F5`), «Разрешения уже даны» (`codex.md П-05`); недо-доверие — повторные «Разрешаю…» на каждый шаг (116 реплик, `П-05`), которые раздражают и не читаются (`methods.md` антипаттерн 1: 93 % одобряют).

### КМ-3. «Готово — это когда я сам открыл и работает, а не когда порт отдаёт 200» (`E-G1`; `r2-screenshots.md S45`; `antigravity P2`)

- **Ошибки:** «Готово» по собственным логам при ошибке 400 в тех же логах (`E-G1`: агент признал); «82/82» при 79+3 skipped (`antigravity P2`); экран расходится со словами агента — 16 реплик (`r2-screenshots.md F1`); на проде — ложное «восстановлено», клиент видит раньше [гипотеза].
- **Объяснимость:** что именно проверено (URL, CI job, трафик), чем (команда/скриншот), когда, независимо ли от исполнителя; «Готово» ставит проверка с неизменяемым списком критериев (`state-visibility G5`).
- **Контроль:** кнопка/действие «проверь живым» с результатом в объекте инцидента; возможность вернуть «не починено» с причиной; закрепить сразу («закоммить/запомни» — `r2-positive.md Н6`).
- **Калибровка:** недо-доверие — после E-G1 пользователь проверяет всё сам и девять раз спрашивает «рабочий код? есть заглушки?» (`E-K3`); пере-доверие — не спросить про «LAN1 остаётся» в сдаче и узнать о сбое через 4,9 сут (`r2-waiting.md` п.2–3).

### КМ-4. «Следи, молчи, пока лежит — но если ты сам умер, я должен это знать» (`E-Q2`; `r2-touchpoints.md N4`)

- **Ошибки:** сторож падает на лимите 297 раз подряд и молчит так же, как «ждём» (`E-Q2`); cron Hermes 8 раз молча (`Э7`); один сбой гасит и работу, и датчик (`N4`); доклад уходит в другую вкладку (`kimi-hermes-pi.md E2`).
- **Объяснимость:** тип тишины [термин-кандидат] — «молчу по решению / не могу работать / жду тебя / лимит до … / сеть» с причиной и сроком (`_critic2.md §5 п.4`); здоровье самого надзора (`state-visibility E8`); время следующего доклада, а не завершения (`state-visibility D6`).
- **Контроль:** список сторожей как объект (не четыре механизма под одним словом — `N2`); правило «будить только ради срочного, важного и действенного» (`state-visibility D2`), заданное пользователем («если пусто — молчи», `claude-code.md E8`); канал доставки по выбору (Telegram/push — один след, `К12`).
- **Калибровка:** пере-доверие — 4,4 сут без единой реплики при мёртвом стороже (`E-Q2`); недо-доверие — «вахту восстанови!!!!», «я не вижу ее в списке вахт» (`codex.md П-10`).

### КМ-5. «Я пошёл спать — чини сам, но платное, снос данных, секреты и необратимое — жди меня» (`claude-code.md S9`; `omg-process.md 7 п.7`; `reports-memory.md` Сценарии)

## 6. Пробелы: чего в свидетельствах нет; что — [гипотеза]; какие наблюдения нужны

### 6.1 Чего нет (по `jtbd.md §3 S14, §5 п.4`; `_critic.md §2`; `_critic2.md §7`)

- **Самой сцены нет.** Ни одного эпизода, где у пользователя падал CI, прод клиента или возникал конфликт слияния в продукте; все сбои в журналах — у харнесса, VPN/роутера/VPS самого пользователя или у вендоров (`standard-scenarios.md C2`: «сбои были у харнесса, не у продукта»; `C3`: конфликты — «нет»).
- **Продукт с клиентами в проде** — [нет свидетельств]: в журналах есть собственные проекты (ARTIGRAM, 45Telega, TG-NEWS, боты, трейдинг — `codex.md 3.1`), но нет эпизода «клиент сообщил, что не работает».
- **CI как сущность** — [нет свидетельств] об использовании CI-уведомлений как триггера; есть только `check:backend` и очередь прогонов внутри OMG (`omg-process.md 2.4`) — это проверки харнесса, не CI продукта.
- **Назначение по событию репозитория** (GitHub Actions, `@copilot`, issue) — [нет свидетельств]; у пользователя назначение всегда репликой в чат или cron (`r2-other-harnesses.md E-Q2`; `codex.md 3.3 п.11`).
- **Что было на экране в момент сигнала** и признак «прочитано» — [нет свидетельств] для любой сцены (`_critic2.md §7`).
- **«Спал / ушёл / ждал» для пауз >6 ч** — не различить (`_critic2.md §7`); для S14 это главный вопрос стадии 6.
- **Эмоции** — только лексика; для S14 нет даже её.
- **Деньги инцидента** — [нет свидетельств] (денег нет нигде, `r2-spend-limits.md §6`).
- **Общение с клиентом/хостером после починки** — [нет свидетельств]; ближайшее — третьи лица в S10 (`jtbd.md §1.3`).
