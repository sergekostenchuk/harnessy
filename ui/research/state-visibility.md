# Видимость состояния длительной автономной работы — исследование

Программа: UX харнесса для работы с моделями и агентами (CJM, сервисный чертёж, IA, три концепции, дизайн-система; планка awards 2026–2027).
Линза: где сейчас процесс, что сделано, что дальше, когда закончится, что пошло не так, что решить.
Дата исследования: 30.09.2026. Файл: `/Users/kostenchuksergey/REPORTS/workbench-design/research/state-visibility.md`.

- **[Ф]** — прочитан сырой файл (JSON/Markdown/PDF/XML), формулировки взяты дословно.

## Резюме (десять находок)

1. **Состояние сводится к малому словарю и группируется по «чей ход».** Agent view в Claude Code: Needs input / Working / Completed, наверху то, что нужно человеку [S38]. Projects: Ready for review / Waiting on you / Working, причём сбой попадает в «Waiting on you» [S39].
2. **Исход работы и жизнь процесса — две оси.** В agent view цвет и анимация показывают состояние работы, а форма значка — жив ли процесс [S38].
3. **Три разных «не ок»:** сбой задачи, сбой инфраструктуры, нет сигнала (Prefect Failed/Crashed [S23]; Grafana Alerting/Error/No Data [S25]; Dagster Warning/Degraded/Unknown [S24]).
4. **Для многочасовой работы процент не нужен.** NN/g даёт процент-индикатор с 10 с и шаги «3 из 50» как альтернативу [S1]; Apple требует честности и запрещает «замирать» [S5]. Для нас: шаги, elapsed, диапазон с пометкой уверенности, расход бюджета.
5. **Внимание — дефицитный ресурс.** Три уровня срочности с зарезервированными цветами (14 CFR 25.1322 [S32]); страницы только по срочному и действенному (Google SRE [S28]); уведомление отсутствующему и с задержкой около 6 с (Claude Code [S42]); одна живая активность вместо нескольких (Apple [S6]).
6. **Подтверждения: от «одобряй каждое» к «наблюдай и вмешивайся».** В Claude Code доля сессий с полным auto-approve растёт с ~20% до >40%, доля прерываний — с 5% до ~9%; агент останавливается сам чаще, чем его прерывают [S46]. Значит, первичный канал — вопросы агента и очередь внимания, а не поток подтверждений.
7. **Стоимость — часть состояния.** Постоянная строка контекст · расход · окно лимита [S40], пороги на факт и на прогноз, оповещение ≠ ограничитель [S31]; провал Replit Agent 3 — расход не виден заранее [S60].
8. **Восстановление после закрытия окна/перезагрузки — показывать, а не подразумевать.** Состояние на диске, рекап «пока вас не было» при возврате [S38]. Урок: до v2.1.248 старая мёртвая сессия всплывала наверх как свежий сбой [S38].
9. **«Готово» выдаёт проверка, а не исполнитель.** Классический сбой долгих агентов — объявить победу рано [S47]. Вывод для вердиктов.
10. **Срок годности.** Пороги NN/g (1993), Harrison (2007), WHO (2009) — фундаментальны, но старые; агентные интерфейсы (agent view, Cursor 3, Antigravity, Copilot) меняются за месяцы, часть в research preview.

## Вопросы

- **Q1.** Как лидеры показывают «где сейчас процесс»: модель состояний, граф, лента, таймлайн?
- **Q2.** Как показывают «что сделано» и «что дальше»: планы, артефакты, сводки?
- **Q3.** Как отвечают на «когда закончится»: ETA, процент, шаги — и когда честнее не обещать?
- **Q4.** Как отличают «что пошло не так» от «что нужно решить» и как выстраивают очередь внимания?
- **Q5.** Как строят иерархию срочности и уведомления (авиация, SRE, Apple/Android, агентные CLI)?
- **Q6.** Как устроены подтверждения, прерывания и эскалации в агентных системах; как меняется поведение людей с опытом?
- **Q7.** Как показывают стоимость и бюджет в реальном времени; где сигнал, где ограничитель?
- **Q8.** Как переживают закрытие окна и перезагрузку; что видит человек, вернувшись?
- **Q9.** Как визуальный язык (цвет, форма, анимация, доступность) поддерживает всё перечисленное?
- **Q10.** Какие метафоры (Mission Control, чек-листы, игровой HUD) дают проверенные приёмы, и что из них переносится?

## Паттерны

Формат: **Имя** · Кто · Что именно · Почему работает · Применимость к харнессу. Объекты харнесса: лестница стадий (дискавери → концепция → OMG L0 … → компиляция), блоки и задачи, прогоны, вердикты, команда агентов (владелец, оркестратор, воркеры, ревьюеры, хранитель), бюджет блока и этапа.

### Сквозные принципы (выведены из паттернов; каждый ссылается на паттерны ниже)

1. **Слово состояния — закрытый словарь с определением.** У каждого слова одно значение, известно, терминальное оно или нет (A1, A6, H1).
2. **Сначала «чей ход», потом «что происходит».** Первая группировка списка — по тому, кто должен действовать (A1, D5).
3. **Живость процесса — отдельная ось от исхода работы** (A2, G1).
4. **Три разных «не ок»:** задача не прошла, инструмент сломался, сигнала нет (A3, A4).
5. **Честный прогресс.** Шаги и факты вместо процента; elapsed всегда, ETA только с указанной уверенностью; не замирать молча (C1–C4).
6. **Три масштаба:** мини-полоска везде, карточка по клику, журнал по запросу; главное состояние видно на верхнем уровне (B1–B3).
7. **Внимание конечно.** Три уровня срочности, уведомляем отсутствующего, счётчик вместо потока, каждое обращение к человеку — с действием (D1–D5).
8. **Ответ там, где увидел вопрос,** и он должен дойти до нужного адресата (B5, E5, AP8).
9. **У каждого числа — возраст и природа** (счёт или оценка) (C7, F1).
10. **Деньги — тоже состояние:** темп расхода, прогнозный порог, жёсткий предел — разные вещи (F1–F3).
11. **Всё переживает закрытие окна;** при возврате — рекап (G1–G3).
12. **Вердикт — запись с основанием; «готово» ставит проверка** (G4, G5).

### A. Модель состояний

**A1. Закрытый словарь состояний, сгруппированный по «чей ход»**
- Кто: Claude Code agent view; Claude Code Projects; GitHub Copilot; Vercel; GitLab.
- Что именно: agent view показывает строки с состояниями Working, Needs input, Idle, Completed, Failed, Stopped; группы в списке — Needs input, Working, Completed (плюс Pinned и Ready for review); «Needs input» — то, что может дать только человек: ответ, решение по разрешению, запрос MCP [S38]. Projects: Overview с группами Ready for review, Waiting on you (включая упавшие потоки), Working [S39]. Copilot: значок-«пилюля» на задаче со всеми активными и завершёнными сессиями [S56]. Vercel: QUEUED, BUILDING, READY, ERROR, CANCELED, DELETED [S18].
- Почему работает: человек видит очередь своих действий, а не хронику процессов. Сбой отнесён к «нужно человеку» (Projects), поэтому нет отдельной «свалки ошибок».
- Применимость: домашний экран харнесса — очередь «ждёт вас» / «идёт» / «готово к проверке» / «завершено»; внутри — лестница стадий. Вывод: у нас несколько сущностей (стадия, блок, прогон, роль), поэтому словарь должен быть общим для всех (см. рабочий словарь ниже).

**A2. Две оси: исход работы и жизнь процесса**
- Кто: Claude Code agent view.
- Что именно: цвет и анимация значка — состояние работы; форма — жив ли процесс: `✻`/анимированный `✽` — процесс жив; `∙` — вышел, но ответ или «прикрепить» перезапустит с того же места; `✢` — цикл `/loop` спит между итерациями, показан счётчик прогонов и обратный отсчёт [S38].
- Почему работает: «Завершено, процесс погашен» и «жив, но ждёт» не путаются; спящий цикл не выглядит зависшим.
- Применимость: у прогона и у ролей харнесса отдельный индикатор «процесс жив / погашен / спит до X». Особенно важно после перезагрузки (G1).

**A3. Сбой задачи ≠ сбой инфраструктуры ≠ нет сигнала**
- Кто: Prefect; Grafana; Dagster; Datadog.
- Что именно: Prefect различает Failed (проблема кода, исключение, нет повторов) и Crashed (инфраструктура: нехватка памяти, выселенный под, сигнал ОС) [S23]. Grafana: Alerting отдельно от No Data (запрос выполнился, точек нет) и Error (не удалось вычислить); опция Keep Last State гасит «мигание» при временных сбоях источника [S25]. Dagster: Unknown — «никогда не материализовалось / нет проверок» [S24]. Datadog: No Data — отдельный статус монитора рядом с OK и Alert [S27].
- Почему работает: реакция человека разная — чинить задачу, чинить окружение или искать, почему молчит источник.
- Применимость: у вердикта и прогона три разных исхода: «не пройдено» (по существу), «сорвалось» (харнесс/окружение/бюджет/лимит), «нет сигнала» (не запускалось, нет данных). Вывод: нужны разные цвета/слова и разные действия рядом.

**A4. Свёртка нескольких сигналов в один статус («наихудший побеждает»), с различием «повтор запланирован»**
- Кто: Dagster+.
- Что именно: единый статус актива берётся как самый повышенный из трёх компонентов — результат последней материализации, свежесть, проверки. Warning — упало, но автоповтор ожидается или проверки с уровнем предупреждения; Degraded — упало без ожидающего повтора, свежесть нарушена, проверки упали; Healthy; Unknown. Статус группируется и фильтруется, есть оповещения на смену статуса [S24].
- Почему работает: один цвет на карточке, а причина — в раскладке по компонентам; «упало, но чинится само» не будит человека.
- Применимость: цвет стадии/блока = худший из: результат прогона, вердикты ревью, состояние бюджета, свежесть данных. Статус «жёлтый: идёт автоповтор» отличается от «красный: повтора нет».

**A5. Пауза на человеке — первоклассное состояние**
- Кто: Prefect; GitLab; GitHub; LangGraph; Magentic-UI.
- Что именно: Prefect Paused (код остановлен до ручного одобрения) и Suspended (процесс завершён) [S23]. GitLab: manual-задачи ждут действия человека; есть «Run all manual» на стадию [S17]. GitHub: задача с обязательными ревьюерами стоит в Pending, ревьюер получает уведомление, решает Approve/Reject с необязательным комментарием [S16]; у check run есть вывод `action_required` [S15]. LangGraph: `interrupt()` сохраняет состояние в чекпойнтере и ждёт сколько угодно [S52]. Magentic-UI: согласие перед необратимыми действиями, частота настраивается пользователем [S51].
- Почему работает: «остановлено ради вас» не выглядит ни как ошибка, ни как работа.
- Применимость: «Ждёт решения владельца» — отдельное состояние у стадии, блока и вердикта, с видимым возрастом ожидания (B5) и объяснением, что именно и кому решать.

**A6. Стадии жизненного цикла с определениями, у каждой — «что известно»**
- Кто: Atlassian Statuspage.
- Что именно: Investigating (симптомы видны, причина неизвестна), Identified (причина найдена, идёт исправление), Monitoring (исправление выкачено, ждём, что симптомы уйдут), Resolved (причина устранена, работа в норме) [S30]. Для каждой заготовлен шаблон сообщения с полем «время следующего обновления» [S29].
- Почему работает: у промежуточного состояния «чиню и наблюдаю» есть имя; не нужно врать «готово» или «не готово».
- Применимость: у вердикта — состояние «проверяется/наблюдаем» между «идёт» и «пройдено»; у блока — «изменение внесено, ждём подтверждающий прогон».

### B. Структура и навигация

**B1. Три масштаба: мини-полоска, граф, журнал**
- Кто: GitLab; GitHub Actions; Airflow; Vercel.
- Что именно: GitLab — мини-граф на коммит (итог по стадиям, стадии раскрываются при наведении), полный граф по стадиям или по зависимостям `needs` [S17]. GitHub — граф заданий с иконкой статуса и линиями зависимостей, обновляется по ходу прогона; клик по заданию открывает его лог [S13]. Vercel — страница деплоя с итогами ресурсов, временем сборки, логами и ошибками [S19].
- Почему работает: состояние видно без раскрытия, детали — по запросу.
- Применимость: мини-полоска лестницы стадий (по одному значку на стадию) на каждом экране и в списке проектов; по клику — граф блоков и зависимостей; ещё глубже — журнал событий прогона. Вывод: у нас уже есть данные (в OM-VIEW `map.json` есть `ladder` с 9 ступенями, статусами и расходом), полоска реализуема без нового сбора.

**B2. Матрица «задачи × прогоны» и таймлайн состояний**
- Кто: Airflow; Grafana.
- Что именно: Airflow Grid — строки-задачи, столбцы-запуски, цвет состояния, фильтры и действия (повтор, пометить, очистить) [S22]. Grafana State timeline — дискретные состояния во времени полосами, «сливает» одинаковые подряд значения, цвета и подписи через value mappings [S26].
- Почему работает: сразу видно «что и с какого прогона ломается» и «сколько времени в каком состоянии».
- Применимость: экран прогонов харнесса (R1/R2/…): строки — блоки или роли, столбцы — прогоны; вторая вкладка — таймлайн состояний ролей (кто когда ждал, работал, был заблокирован).

**B3. «Где ждёт сейчас»: ожидающие элементы и стек ожидания**
- Кто: Temporal Web UI.
- Что именно: для выполнения показаны Pending Activities (активные и ожидающие), Call Stack — где код ждёт сейчас; четыре вида истории: Timeline, Compact (группировка активностей, сигналов, таймеров), All, JSON; действия — отмена, сигнал, сброс, завершение; сохранённые представления и поисковые атрибуты для фильтрации [S20][S21].
- Почему работает: отвечает на «почему стоит» без чтения полного журнала.
- Применимость: у каждого зависшего блока — «ждёт: ответ ревьюера / решение владельца / слот бюджета / внешний вызов», с временем ожидания. Компактный вид истории — как основной, полный — по кнопке.

**B4. Строка-сводка «что делает сейчас» с ограничением частоты обновления**
- Кто: Claude Code agent view; status line.
- Что именно: одна строка на сессию — что делает, что нужно или что получено; сводку пишет модель класса Haiku, при этом при активной работе текст обновляется не чаще раза в 15 секунд из собственного вывода сессии без запроса к модели; при долгом ходе модель переписывает сводку раз в несколько минут; в заблокированной строке показан сам вопрос [S38]. Status line: дебаунс обновлений 300 мс, опциональный `refreshInterval` от 1 с [S40]. Возраст строки отсчитывается от создания и замораживается на длительности прогона у завершённых [S38].
- Почему работает: живая, но не мигающая; дёшево; заблокированная строка сразу показывает вопрос.
- Применимость: одна строка на роль и на блок, обновление — по событиям и не чаще N секунд; при блокировке — сам вопрос; у завершённого — итог и «замороженное» время работы.

**B5. Peek: ответить, не открывая транскрипт**
- Кто: Claude Code agent view.
- Что именно: по пробелу открывается панель: точная формулировка вопроса, или результат, или полное предложение статуса; список связанных PR; для ожидающей сессии строка вида `waiting 3m`; варианты ответа — нумерованным списком, число выбирает вариант; для остальных `Tab` подставляет предложенный ответ; неотправленный ответ сохраняется и уходит следующим сообщением [S38].
- Почему работает: цикл «увидел вопрос — ответил» занимает секунды; человек не тонет в транскрипте.
- Применимость: панель быстрых действий на очереди «ждёт вас» — вопрос, варианты кнопками, предложенный ответ, время ожидания; недоставленное — в очередь на повторную отправку.

**B6. Сводка результата на странице прогона, а не в логе**
- Кто: GitHub Actions; Antigravity; Replit; Copilot.
- Что именно: GitHub — Markdown-сводка задачи на странице прогона (до 1 МиБ на шаг, показывается до 20 сводок на задачу) и аннотации error/warning/notice со ссылками на место [S14]. Antigravity — принцип «проверяй по артефактам, не по логам» [S49]. Replit Agent 3 — периодически тестирует приложение и присылает сводку тестов, тестирует когда «достаточно изменилось» [S60]. Copilot — подагенты в логах свёрнуты по умолчанию с индикатором статуса, разворачиваются по желанию [S54].
- Почему работает: человек читает итог и аномалии, а не поток.
- Применимость: у каждого прогона и вердикта — короткая сводка (что проверено, что не прошло, что осталось), аннотации привязаны к узлам/файлам, подагенты и воркеры свёрнуты со статусом.

**B7. Артефакты как поверхность прогресса и согласования**
- Кто: Google Antigravity; Anthropic (harness); Claude Code.
- Что именно: Antigravity — структурные результаты агента (планы реализации, списки задач, скриншоты, записи браузера) для проверки без прокрутки вызовов инструментов; комментарии прямо на артефакте, агент учитывает их, не останавливаясь; политики ревью настраиваются; терминальные уведомления, когда нужно одобрить изменённые файлы [S49][S50]. Anthropic — между окнами контекста состояние держат файл прогресса, `feature_list.json` с полем `passes`, история git и скрипт инициализации [S47].
- Почему работает: у процесса есть устойчивые «предметы», к которым можно вернуться и на которые можно указать.
- Применимость: у харнесса есть свои артефакты (план стадии, карта блоков, вердикты); их нужно показывать как основную поверхность, лента чата — вторична.

**B8. Единый список всех агентов независимо от места запуска**
- Кто: Cursor 3; Antigravity; Claude Code.
- Что именно: Cursor Agents Window — все локальные и облачные агенты в боковой панели, включая запущенные с мобильного, веба, десктопа, Slack, GitHub и Linear; перенос между локальным и облачным выполнением; облачные агенты показывают демо и скриншоты [S58]. Antigravity Manager — интерфейс для запуска, оркестрации и наблюдения многих агентов в разных рабочих пространствах [S49]. Claude Code desktop — боковая панель сессий с фильтром по статусу, проекту, окружению [S44].
- Почему работает: один экран «что у меня запущено», независимо от того, где оно работает.
- Применимость: единый список ролей и прогонов по всем проектам с фильтрами по статусу/проекту/роли.

### C. Время, ETA, прогресс

**C1. Порог 10 секунд и переход от процента к «шагам и фактам»**
- Кто: NN/g; Apple.
- Что именно: 0,1 с — ощущение мгновенной реакции; 1 с — сохранение потока мысли; 10 с — предел удержания внимания [S2]. Циклическая анимация — для ожиданий 2–10 с; для 10+ с — индикатор процента; для неизвестного объёма — показывать текущие факты (пример «Updating address 3 of 50»), шаги вместо процентов, общие оценки времени вместо точных чисел [S1]. Исследование, на которое ссылается NN/g (университет Небраски-Линкольна), — люди с движущимся индикатором были готовы ждать в среднем втрое дольше [S1].
- Почему работает: человек понимает, что процесс жив, и решает — ждать или заняться другим.
- Применимость: наши процессы длятся минуты и часы, поэтому порог 10 с — лишь нижняя граница; главное правило переносится: показывай факты и шаги (блок 4 из 9, ревью 2 из 3), а не вращающийся индикатор. Пороги применимы к микровзаимодействиям (отправка, открытие экрана).

**C2. Честность прогресса: определённый/неопределённый, не замирать**
- Кто: Apple.
- Что именно: по возможности определённый индикатор; неопределённый не помогает оценить время; сообщать продвижение честно и по возможности выравнивать темп («90% за пять секунд и остаток за пять минут» выглядит как обман); индикатор должен двигаться — неподвижный воспринимается как зависание, а при задержке нужно объяснить проблему и действия; при появлении оценки переключать неопределённый на определённый; не менять круг на полосу; подпись — конкретная, без пустых «loading»; индикатор — в постоянном месте; по возможности давать Cancel, а при потерях — Pause и предупреждение [S5].
- Почему работает: доверие к индикатору сохраняется.
- Применимость: индикатор прогресса блока — только после того, как известен объём (число задач из плана); до этого — «шаг N: что делается сейчас» и elapsed. Остановка прогона — с предупреждением о потерях и с возможностью паузы.

**C3. Elapsed всегда; remaining — только когда откалиброван**
- Кто: Tan, Nov (2026, препринт).
- Что именно: при системных ожиданиях 10/30/60 с обратный отсчёт оставшегося времени увеличил раздражение по сравнению со счётчиком прошедшего; отсутствие времени делало ожидание более долгим и неопределённым; на успех последующей задачи это не повлияло [S11]. Apple: определённый индикатор помогает решить — ждать, запустить позже или отменить [S5].
- Почему работает: elapsed не обещает того, чего нельзя выполнить, но снимает неопределённость.
- Применимость: вывод. Всегда elapsed («работает 42 мин»); оценка оставшегося — только диапазон и только если есть история сопоставимых прогонов, с пометкой «оценка»; иначе не показывать. Оговорка: исследование про секунды, для часов данных не нашёл.

**C4. Порядок стадий и «честное ускорение»**
- Кто: Harrison et al.; NN/g.
- Что именно: паузы воспринимаются как удлиняющие ожидание; ускоряющийся прогресс предпочитают; эффекты сильнее ближе к концу; терпимость к «плохому» поведению прогресса выше в начале, поэтому нестабильные и медленные этапы лучше ставить первыми [S10]. NN/g советует начинать медленнее и ускоряться, чтобы не задавать ожиданий, которые не удержать [S1].
- Почему работает: пик и конец опыта определяют оценку.
- Применимость: в планировании этапов — раньше идут неопределённые по длительности шаги (внешние вызовы, ресёрч). Ограничение: Apple требует честности [S5]; использовать порядок работ, а не рисовать индикатор с искажённой шкалой.

**C5. Вехи и отрезки на линии пути**
- Кто: Android 16 progress-centric notifications; Apple Live Activities.
- Что именно: Android — Segments обозначают состояния и длительность (можно красить, например пробки), Points — вехи и смену состояний (приготовление, доставка, посадка) [S8]. Apple: Live Activity — для задач с определённым началом и концом, обычно не дольше восьми часов [S6].
- Почему работает: линия пути содержит вехи, а не только «сколько процентов».
- Применимость: лента стадий как линия с вехами (стадия пройдена, вердикт получен, ждём решения), отрезки покрашены по состоянию; активность имеет конец и итог.

**C6. Живость без шума**
- Кто: Vercel Geist; Apple; Claude Code.
- Что именно: Vercel — анимируются только QUEUED и BUILDING, терминальные состояния статичны; цвет меняется только при реальной смене `readyState`, а не на каждый опрос; рядом с точкой — относительное время («Building · 12s ago») [S18]. Apple: анимации Live Activity до двух секунд; на Always-On анимации нет [S6]. Claude Code: мигание счётчика «← 2 agents» отключается настройкой reduced motion [S38].
- Почему работает: анимация — сигнал «работа идёт»; всё статичное — «закончено»; нет ложных сигналов.
- Применимость: правило дизайн-системы — движение = нетерминальное состояние; «возраст последнего события» рядом с индикатором как пассивный признак жизни.

**C7. Возраст и природа у каждого числа**
- Кто: Claude Code; Vercel; ваш OM-VIEW.
- Что именно: `/usage` при недоступности сервера показывает последние известные полосы использования с пометкой «Showing last-known usage» и давностью [S45]. Стоимость в status line — оценка по прайс-листу, «может отличаться от реального счёта» [S40]. В OM-VIEW время не-якорных событий восстановлено интерполяцией и помечено «≈» (README проекта). Vercel — относительное время рядом со статусом [S18].
- Почему работает: человек не принимает устаревшее или оценочное за факт.
- Применимость: правило: каждое число имеет значок «оценка/счёт» и возраст; устаревшее — визуально приглушено.

### D. Внимание и уведомления

**D1. Три уровня срочности с зарезервированными цветами**
- Кто: FAA (14 CFR 25.1322).
- Что именно: Warning — немедленное внимание и немедленный ответ; Caution — немедленное внимание, ответ позже; Advisory — внимание, ответ возможно позже. Warning и Caution подаются как минимум через два канала (звук, зрение, тактильно) и допускают подтверждение с приглушением сигнала; система оповещения обязана минимизировать ложные и лишние оповещения; средство подавления сигнала при отказе самой системы оповещения не должно быть настолько доступным, чтобы сработать случайно или по привычке, а подавление должно явно индицироваться; оповещение снимается, когда условие исчезло; красный — Warning, янтарный/жёлтый — Caution, для Advisory — любой цвет кроме красного и зелёного; на монохромных экранах уровни различают иным кодированием; использование красного, янтарного и жёлтого для других функций должно быть ограничено, чтобы не мешать оповещениям [S32].
- Почему работает: срочность различима без чтения; цвета не размыты декоративным использованием.
- Применимость: три уровня в харнессе: «блокирует прогон сейчас» (красный), «нужно решение, прогон не стоит» (жёлтый), «к сведению» (нейтральный). Красный и жёлтый зарезервированы за этим, не использовать для декоративного акцента и «бренда». Алерт исчезает сам, когда условие снято.

**D2. Будить человека только ради срочного, важного и действенного**
- Кто: Google SRE.
- Что именно: страница — для необнаруженного иначе, срочного, действенного и видимого пользователю состояния; требует осмысленного человеческого ответа, а не робота; фокус на симптомах, не причинах; страницы достаточно редки, чтобы реагировать всерьёз; при частых страницах люди начинают пролистывать; для малозначимого — дашборд [S28].
- Почему работает: доверие к уведомлению сохраняется.
- Применимость: критерий допуска для любого пуша владельцу: срочно, действенно, ранее не видно. Остальное — в очередь внутри интерфейса. Вывод: у харнесса нужно заранее перечислить, какие события вообще имеют право будить (примерно: ожидание решения, необратимый шаг, срыв прогона, порог бюджета).

**D3. Уведомлять отсутствующего и с задержкой**
- Кто: Claude Code hooks; Apple.
- Что именно: Notification-тип `permission_prompt` срабатывает, если запрос разрешения ждёт около шести секунд; `idle_prompt` — когда ответ закончился около 60 секунд назад и вы ничего не вводили; в терминале эти типы видны, только когда вы, судя по всему, отошли; `agent_needs_input` и `agent_completed` — когда открыт agent view [S42]. Apple: если приложение на переднем плане, не показывать уведомление, а спокойно вставить данные в текущее представление [S7].
- Почему работает: присутствующему не нужен звонок, отсутствующему — нужен.
- Применимость: логика присутствия: активен ли пользователь в окне; если да — только индикатор, если нет — через N секунд уведомление. Задержки как настройки.

**D4. Одна живая «активность» на событие; конец задан; хвост-итог**
- Кто: Apple Live Activities; Android Live Updates.
- Что именно: одна Live Activity вместо нескольких — с ротацией событий; обновлять только при новом содержимом; оповещать только о существенном и не дублировать push; завершать сразу по окончании; итог может оставаться до четырёх часов на Lock Screen, разумно 15–30 минут; не рекламировать; не показывать чувствительное; кнопка — одна, для действий «один раз или пауза/продолжить»; тап ведёт в нужное место приложения [S6]. Android: только текущая активность с началом и концом, инициированная пользователем и требующая внимания на протяжении всего процесса; не для рекламы, чатов, оповещений, будущих событий; отслеживание посылки — как пример неподходящего; действие Unpin; отклонённые обновления не публиковать повторно, иначе пользователи отзывают разрешение [S9].
- Почему работает: один компактный объект на «идущее сейчас» вместо потока.
- Применимость: «активный прогон» — единый компактный объект (полоска в шапке, в трее, в мобильном виджете) с состоянием, elapsed, кнопкой одного действия и ссылкой в нужное место; по завершении — итог на 15–30 минут, затем уходит в историю; возможность отписаться от активности.

**D5. Счётчик «ждут вас» в постоянных якорях и настраиваемые каналы**
- Кто: Claude Code; Apple.
- Что именно: в подвале обычной сессии — счётчик фоновых агентов, ждущих вас (`← 2 agents`, потом `← 2 done`), обновление около каждых десяти секунд, короткая смена цвета при изменении, отключается reduced motion; в заголовке вкладки терминала — число ожидающих ввода [S38]. В Projects на кнопке Overview точка при ожидании потока; уведомления можно включить на каждый завершённый ход или выключить для проекта [S39]. Десктоп: ОС-уведомление, когда сессия завершила задачу, а вы её не смотрите; push на телефон, когда Dispatch-сессия закончила или ждёт подтверждения [S44]. Apple: значок-бейдж только для непрочитанных уведомлений; не полагаться на него как на единственный канал важной информации [S7].
- Почему работает: якорь виден отовсюду; каналы выбирает человек.
- Применимость: счётчик в заголовке окна, вкладке и меню-баре; уведомления настраиваются по проекту, событию и уровню срочности (D1).

**D6. Обещай время следующего сообщения, не время завершения**
- Кто: Atlassian Statuspage.
- Что именно: в каждом шаблоне поле «следующее обновление через …»; пояснение: не нужно обещать, что исправление будет готово, достаточно сказать, когда будет следующее сообщение; оно может повторять «всё ещё работаем»; цель — чтобы люди знали, что вы на связи, и не заваливали поддержку вопросами [S29].
- Почему работает: обещание выполнимо, тревога снимается.
- Применимость: у прогона — «следующий отчёт в HH:MM» (плановый пульс), даже если новостей нет; отчёт о том, что новостей нет, — отдельный тихий тип (без звука). Вывод: сочетается с Apple («обновлять только при новом содержимом» [S6]): пульс показываем пассивно, а не уведомлением.

### E. Подтверждения и вмешательство

**E1. Настраиваемая лестница автономии — и что известно о поведении людей**
- Кто: Claude Code; Anthropic; Smashing.
- Что именно: режимы Claude Code — default/manual (без вопросов только чтение), acceptEdits, plan, auto, dontAsk, bypassPermissions; для auto в таблице режимов указано назначение: долгие задачи и снижение усталости от подтверждений (prompt fatigue) [S41]. Smashing: четыре уровня — Observe & Suggest, Plan & Propose, Act with Confirmation, Act Autonomously (с уведомлением после действия) [S59]. Данные Anthropic по Claude Code: у новичков (<50 сессий) около 20% сессий с полным auto-approve, у опытных (750+) — больше 40%; прерываний — около 5% ходов у новичков и около 9% у опытных; на самых сложных задачах Claude Code запрашивает уточнение более чем вдвое чаще, чем его прерывают люди; вывод авторов — пошаговое одобрение теряет смысл с ростом числа шагов, нужны надёжная видимость и простые механизмы вмешательства [S46].
- Почему работает: режим соответствует уровню доверия и риску.
- Применимость: у каждой стадии/блока — явный уровень автономии, видимый в шапке (аналог индикатора режима). Вывод: интерфейс должен оптимизироваться под «наблюдай и вмешивайся» — кнопка прерывания всегда под рукой, а запросы агента — главный вход в очередь внимания.

**E2. Превью намерения и редактор плана до выполнения**
- Кто: Magentic-UI; Antigravity; Claude Code plan mode; Smashing.
- Что именно: Magentic-UI — ко-планирование: пользователь правит план в редакторе или текстовой обратной связью до запуска; ко-исполнение: видны предстоящие действия и наблюдения, можно поставить на паузу и взять управление; в тесте GAIA с симулированным пользователем успех вырос с 30,3% до 51,9%, помощь запрашивалась в 10% задач [S51]. Antigravity — Implementation Plan как проверка перед изменением кода [S50]. Claude Code plan mode — правки заблокированы до утверждения плана [S41]. Smashing: Intent Preview [S59].
- Почему работает: дешевле поправить план, чем откатить результат.
- Применимость: перед каждым необратимым шагом (запуск прогона, расход бюджета, слияние) — показать намерение: что будет сделано, чем рискуем, критерии успеха и провала; принять/изменить/отклонить.

**E3. Опрос GO/NO-GO по ролям и чек-лист с паузами**
- Кто: NASA Mission Control; WHO.
- Что именно: перед крупными событиями руководитель полёта «обходит комнату» и опрашивает подсистемы: ответственный контролёр говорит GO или NO-GO; при NO-GO событие откладывается или прерывается; каждый контролёр — эксперт по своей системе; любой может потребовать прерывания; каждая консоль подписана сокращением по зоне ответственности [S34]. Руководитель полёта сидит около середины зала для координации [S36]; capcom — человек, говорящий с астронавтами [S35]. WHO — чек-лист на трёх фиксированных паузах (Sign In, Time Out, Sign Out), участие всей команды и словесное подтверждение [S33].
- Почему работает: решение принимается по явным ответам ответственных, а не по «вроде всё нормально».
- Применимость: «опрос» перед необратимым шагом: каждая роль (ревьюер, хранитель, исполнитель, бюджет) — зелёный/красный с подписью и основанием; сводная панель у ведущего; любая роль может остановить. Три фиксированные паузы на стадии: до старта, перед необратимым шагом, при сдаче.

**E4. Комментарий на артефакт и «руление» без остановки агента**
- Кто: Antigravity; GitHub Copilot.
- Что именно: Antigravity — комментарии на артефакт, агент учитывает их, не останавливая выполнение [S49]. Copilot — во время сессии можно отправить сообщение в чате или комментарием в Files changed, агент подстраивается после завершения текущего вызова инструмента; каждое сообщение расходует AI credits; кнопка Stop session завершает прогон и сохраняет уже отправленные коммиты [S53][S57].
- Почему работает: человек влияет на ход, не ломая его; цена вмешательства видна.
- Применимость: вмешательство двух видов — «замечание» (мягко, учтётся на следующем шаге) и «стоп» (жёстко, с сохранением сделанного); рядом с кнопкой — цена в расходе, если она есть.

**E5. Вопрос агента: варианты, предложенный ответ, время ожидания**
- Кто: Claude Code agent view; Projects.
- Что именно: см. B5. Дополнительно: разрешение на команду в peek показывается как текст без вариантов, а ответить можно, введя текст или прикрепившись к сессии [S38]. В Projects подтверждение живёт в потоке; сказать «продолжай» в общем разговоре проекта не доходит до потока [S39].
- Почему работает / предупреждение: ответ должен доходить до адресата; интерфейс обязан показывать, куда именно он уйдёт.
- Применимость: любой вопрос в очереди внимания содержит адресата (роль/поток) и после отправки — подтверждение «доставлено».

**E6. Пауза с сохранением состояния и корректное возобновление**
- Кто: LangGraph; Prefect.
- Что именно: `interrupt()` работает через чекпойнтер и идентификатор потока, состояние сохраняется и может ждать неограниченно; возобновление через `Command(resume=value)`; узел при возобновлении выполняется с начала, поэтому операции до `interrupt()` должны быть идемпотентными; при нескольких прерываниях ответы сопоставляются по идентификаторам [S52]. Prefect Suspended — процесс завершён, но возобновление возможно [S23].
- Почему работает: пауза переживает перезапуск.
- Применимость: в UI у паузы значок «сохранена на диске» и, при возобновлении, предупреждение, если шаг небезопасен к повтору. Вывод из документации: повтор кода до паузы — источник дублей, значит, «возобновить» должно показывать, что будет выполнено заново.

**E7. Откат и стоп с сохранением**
- Кто: Claude Code checkpointing; Copilot; Apple.
- Что именно: чекпойнт создаётся на каждый ход; хранятся снимки 100 последних; `/rewind` предлагает варианты: восстановить код и разговор, только разговор, только код, сжать разговор [S43]. Copilot Stop сохраняет уже отправленные коммиты [S57]. Apple: если отмена ведёт к потерям, предупредить и предложить Pause [S5].
- Почему работает: цена вмешательства ограничена, что снижает страх нажать.
- Применимость: у каждого блока — «вернуться к точке» с явным списком того, что откатывается (код / решения / расход не откатывается). Расход и внешние действия не откатываются — это надо писать прямо.

**E8. Метрики здоровья самого надзора**
- Кто: Smashing (предложения автора); Anthropic (описание).
- Что именно: Smashing предлагает ориентиры — принятие превью без правок >85%, доля откатов <5%, частота эскалаций 5–15% с успешным восстановлением >90%, отслеживание смен настроек автономии; это рекомендации автора статьи, не результат исследования [S59]. Anthropic описывает наблюдаемое поведение (доли auto-approve, прерываний), не целевые значения [S46].
- Почему работает: видно, не превратился ли надзор в формальность.
- Применимость: собирать у себя те же метрики (доля принятых превью, откатов, эскалаций, время ожидания решений) и не принимать чужие числа как норму.

### F. Стоимость и бюджет

**F1. Постоянная строка «контекст · расход · окно лимита · усилие»**
- Кто: Claude Code status line; `/usage`.
- Что именно: status line получает JSON с полями: `context_window.used_percentage`, `cost.total_cost_usd` (оценка по прайс-листу, может отличаться от счёта; сбрасывается на `/clear`), `cost.total_duration_ms`, `rate_limits.five_hour` и `seven_day` (`used_percentage`, `resets_at`), `effort.level`, `spend_limit` за шлюзом [S40]. `/usage` показывает блок сессии, полосы плана и разбивку; кредиты и лимит расходов; при ошибке — последние известные значения с давностью [S45]. Копилот: каждое сообщение-руление расходует AI credits, то есть цена видна в месте действия [S57].
- Почему работает: расход и запас всегда на глазах, а не в отдельном отчёте.
- Применимость: строка в шапке: расход блока / бюджет блока, расход этапа / бюджет этапа, темп, окно лимитов провайдера и время сброса; всё помечено «оценка/счёт» и возрастом.

**F2. Пороги на факт и на прогноз; оповещение ≠ ограничитель**
- Кто: Google Cloud Billing; Claude Code.
- Что именно: пороги по умолчанию 50%, 90%, 100% от бюджета по фактическому расходу; порог по прогнозируемому расходу отдельно; бюджет только с оповещениями сам расход не ограничивает; для автоматических действий — Pub/Sub [S31]. Claude Code: при достижении лимита расходов предлагает поднять или снять лимит прямо в CLI [S45].
- Почему работает: заранее видно, что бюджет идёт к пределу; ясно, что оповещение и стоп — разные вещи.
- Применимость: у блока и этапа пороги на факт и на прогноз; у бюджета явный тип — «сигнал» или «ограничитель»; при ограничителе — понятная кнопка «поднять лимит» с указанием, кто может.

**F3. Множитель команды: мультиагентность стоит кратно**
- Кто: Anthropic.
- Что именно: агенты расходуют около 4× токенов относительно чата, мультиагентные системы — около 15× [S48].
- Почему работает: человек понимает цену «запустить команду».
- Применимость: при создании команды агентов — оценка множителя расхода перед стартом (вывод: показать диапазон до запуска, а не после).

### G. Восстановление и доверие

**G1. Состояние на диске, перезапускаемый процесс, здоровье самой системы**
- Кто: Claude Code agent view; Airflow; Anthropic.
- Что именно: отдельный процесс-супервизор ведёт фоновые сессии, закрытие agent view или оболочки их не останавливает; состояние сессий хранится на диске и переживает автообновление и перезапуск супервизора; сон машины не считается простоем, процессы возобновляются и переподключаются; выключение всё же останавливает сессии [S38]. Airflow: на главной — индикаторы здоровья компонентов (метабаза, планировщик, triggerer, dag-процессор) [S22]. Anthropic: системы строят так, чтобы продолжать с чекпойнта, а не с начала; rainbow-выкладки не рвут работающих агентов; полная трассировка в проде помогает диагностировать [S48].
- Почему работает: человек уверен, что закрыл окно — работа не пропала, а если пропала — видно почему.
- Применимость: индикатор «здоровье харнесса» (шина, каналы, хранилище, воркеры) отдельно от здоровья проекта; при перезагрузке — состояние «восстанавливается: N ролей вернулось, M ждут».

**G2. Рекап «пока вас не было»**
- Кто: Claude Code agent view.
- Что именно: при подключении к сессии Claude публикует короткий пересказ того, что произошло за время отсутствия [S38].
- Почему работает: возврат без перечитывания журнала.
- Применимость: экран возврата: что завершилось, что требует решения, что сорвалось, сколько потрачено — в порядке важности (см. D1).

**G3. Не поднимать устаревший сбой наверх; спрашивать перед возобновлением старого**
- Кто: Claude Code agent view (журнал версий).
- Что именно: с v2.1.248 фоновая сессия, найденная мёртвой более чем через 48 часов после последней активности (например, компьютер был выключен несколько суток), показывается как Stopped с пометкой, что завершена, пока служба была выключена; Enter спрашивает перед возобновлением. Раньше такая сессия возвращалась свежим сбоем наверху списка, а один Enter втягивал недельный разговор на передний план [S38].
- Почему работает: старое не маскируется под новое.
- Применимость: после долгой паузы старые «сорвалось» переходят в «остановлено по выключению», не поднимаются в очередь внимания; возобновление старого — с подтверждением и показом возраста.

**G4. Трассировка результата к сессии и логам**
- Кто: GitHub Copilot; Claude Code.
- Что именно: в коммит агента добавляется трейлер `Agent-Logs-Url` со ссылкой на полные логи сессии — для ревью и аудита [S55]; логи сессии рядом с Overview и Files changed [S53]; в agent view у строки — метка PR со статусом цветом: жёлтый — ждёт проверок/ревью или проверки упали, зелёный — проверки прошли, фиолетовый — слит, серый — черновик/закрыт [S38].
- Почему работает: от результата всегда можно дойти до «кто, когда, почему».
- Применимость: у каждого вердикта и артефакта — ссылка на прогон, роль и основание; статус результата цветом на строке.

**G5. «Готово» выдаёт проверка: неизменяемый список критериев с полем passes**
- Кто: Anthropic (harness для долгих агентов).
- Что именно: список требований в JSON с полем `passes`; агенту разрешено менять только это поле, править сами тесты нельзя; наблюдавшиеся провалы — попытка сделать всё сразу и исчерпать контекст, преждевременное объявление проекта завершённым, отметка «готово» без сквозной проверки, оставление окружения в неописанном сломанном состоянии [S47].
- Почему работает: «готово» перестаёт быть словом исполнителя.
- Применимость: вывод для вердиктов: состояние «пройдено» выставляет ревьюер/проверка по зафиксированным критериям, исполнитель может заявить «готово к проверке» (A1), но не «пройдено».

### H. Визуальный язык

**H1. Состояние = цвет + форма + слово**
- Кто: Vercel Geist; FAA; Claude Code.
- Что именно: Vercel — у каждого состояния свой заголовок и подпись, чтобы дальтоники получали ту же информацию; `aria-label` собирается автоматически; декоративную точку скрывают от скринридера, если рядом подписано состояние [S18]. FAA — на монохромных экранах разница между уровнями кодируется иначе, чем цветом [S32]. Claude Code — значок кодирует состояние работы цветом и анимацией, а жизнь процесса — формой; подсказка со счётчиком скрывается в режиме скринридера [S38].
- Почему работает: не полагается на цвет.
- Применимость: правило дизайн-системы — каждое состояние имеет цвет, форму значка и слово; проверка на дальтонизм и на монохром.

**H2. Состояние — на самом объекте; глобальный слой — сводка (по аналогии, низкая уверенность)**
- Кто: Chalmers, Fagerholt & Lorentzon.
- Что именно: тезис классифицирует элементы интерфейса игр по представлению: диегетические (часть мира игры), недиегетические (оверлей), пространственные (внутри 3D-геометрии, но вне вымысла), мета; обычные интерфейсы шутеров в основном недиегетические, то есть накладываются оверлеем [S37]. Правило «показывать HUD только когда актуально» в первоисточнике не найдено (только вторичные обзоры) — не подтверждено.
- Почему работает: даёт язык для разговора о том, где живёт информация.
- Применимость: вывод по аналогии — состояние лежит на самом объекте (узел карты, строка блока), а глобальная шапка — сводка и очередь. Не использовать как доказательство эффективности.

## Антипаттерны и провалы

- **AP1. Вечный спиннер и статичный «Loading…».** NN/g: циклическая анимация только для 2–10 с; в длинных ожиданиях люди не понимают, завис ли процесс [S1]. Apple: неподвижный индикатор читается как зависание [S5].
- **AP2. Прогресс-обман.** Быстрые 90% и долгий остаток [S5]; тем более рисование шкалы «для восприятия» вопреки данным [S10 против S5].
- **AP3. «Всё красное» и усталость от предупреждений.** SRE: при частых страницах люди пролистывают и игнорируют [S28]; FAA: ложные и лишние оповещения нужно минимизировать [S32]; Claude Code: режим auto создан ради снижения усталости от подтверждений [S41].
- **AP4. Оповещать о причинах, а не о симптомах.** SRE: симптомы (HTTP 500) вместо причин (БД не принимает соединения) [S28].
- **AP5. Дублирование каналов и повторные уведомления.** Apple: не слать несколько уведомлений об одном; не сочетать push и Live Activity для тех же обновлений; ошибки — не уведомлением, а алертом [S6][S7]. Android: отклонённые Live Updates не публиковать заново, иначе пользователи отзывают разрешение [S9].
- **AP6. Скрытая или непрогнозируемая стоимость.** The Register сообщил о жалобах на скачок расходов после запуска Replit Agent 3 (по цитатам в статье — от 70 долларов за ночь до 1000 за неделю; жалобы касались и непрозрачности расчёта; ответ Replit на момент публикации получен не был) [S61]. Разбор причин и последующих изменений не проверял. Замена: F1–F3.
- **AP7. «Готово» ставит исполнитель.** Наблюдавшиеся провалы долгих агентов: преждевременное объявление завершения, отметка без сквозной проверки, недокументированное сломанное окружение [S47]. Замена: G5.
- **AP8. Подтверждение не в том канале.** В Projects слово «продолжай» в общем разговоре не доходит до потока, ждущего разрешения [S39]; в peek разрешение на команду нельзя выбрать кнопкой — нужно ответить текстом или подключиться [S38]. Замена: показывать адресата и подтверждать доставку (E5).
- **AP9. Старый сбой выглядит свежим.** До v2.1.248 сессия, найденная мёртвой спустя дни, всплывала как новый сбой наверху, а Enter сразу возобновлял старый разговор [S38]. Замена: G3.
- **AP10. Бейдж — единственный канал.** Apple: бейдж могут выключить; важное должно быть заметно при открытии приложения [S7].
- **AP11. Только цвет.** Vercel и FAA требуют дублировать смысл словом/формой/кодированием [S18][S32].
- **AP12. Мигание состояния (flapping).** Grafana предлагает Keep Last State и pending-период, чтобы оповещение не срабатывало, снималось и срабатывало снова из-за временных сбоев источника [S25]. Vercel: цвет меняется только при реальной смене состояния, не на каждый опрос [S18].
- **AP13. Только обратный отсчёт оставшегося времени.** В коротких ожиданиях он раздражал сильнее, чем счётчик прошедшего; отсутствие времени — тоже плохо [S11] (ограничение: 10–60 с, препринт).
- **AP14. Live-активность для того, что не требует постоянного внимания.** Android: отслеживание посылки — пример неподходящего [S9]. Для нас: не делать «активность» из фоновых событий без действия.
- **AP15. Возобновление, повторяющее побочные эффекты.** LangGraph: узел при возобновлении выполняется с начала, побочные эффекты до `interrupt()` повторяются [S52]. Для UI: «возобновить» должно показывать, что будет повторено.
- **AP16. Считать «нет данных» нормой.** Grafana и Dagster выделяют No Data/Unknown отдельно [S25][S24]; Datadog включает No Data как статус, но подробное поведение на прочитанной странице не описано [S27].

## Критерии/чек-лист

Проверяемые критерии для дизайна и приёмки. Числа взяты из источников; там, где это моё решение, помечено «наш критерий».

**Состояния**
- [ ] Словарь состояний закрыт, у каждого слова есть определение, терминальность и чей ход (A1, A6). Наш критерий: одно слово — одно состояние на всех экранах.
- [ ] Ось «процесс жив/погашен/спит» отделена от исхода (A2).
- [ ] Три исхода различимы: не пройдено / сорвалось / нет сигнала (A3).
- [ ] Итоговый цвет сущности = худший из компонентов, причины раскрываются (A4).
- [ ] Ожидание человека — отдельное состояние с возрастом ожидания (A5, B5).
- [ ] Промежуточное «проверяется/наблюдаем» существует (A6).

**Структура**
- [ ] Мини-полоска стадий видна на каждом экране; граф и журнал — по запросу (B1).
- [ ] Есть матрица блоки × прогоны и таймлайн состояний ролей (B2).
- [ ] Для каждого зависшего элемента показано, чего именно он ждёт (B3).
- [ ] Строка «что делает сейчас» обновляется не чаще заданного интервала; у Claude Code — 15 с без обращения к модели (B4). Наш критерий: интервал — параметр.
- [ ] Подагенты/воркеры свёрнуты со статусом (B6).

**Время и прогресс**
- [ ] Всегда есть elapsed; оценка оставшегося — диапазон с пометкой «оценка» и только при калибровке (C3).
- [ ] До известного объёма — шаги и факты, не процент; после — переключение на определённый, без смены формы индикатора (C1, C2).
- [ ] Индикатор никогда не стоит молча: при задержке — объяснение причины и действий (C2).
- [ ] Анимация только у нетерминальных состояний; терминальные статичны; длительность анимаций ≤2 с (по Apple [S6]); учитывается reduced motion (C6).
- [ ] Цвет меняется только при реальной смене состояния (C6).
- [ ] У каждого числа — возраст и метка «оценка/счёт» (C7).

**Внимание**
- [ ] Три уровня срочности; красный и жёлтый зарезервированы только за ними (D1).
- [ ] Оповещение снимается само, когда условие исчезло; подавление не может сработать случайно и всегда явно индицируется (D1).
- [ ] Список событий, имеющих право будить, зафиксирован; каждое: срочно, действенно, ранее не видно (D2).
- [ ] Уведомление отсутствующему после задержки (в Claude Code — около 6 с для разрешения, около 60 с простоя) и только индикатор присутствующему (D3). Наш критерий: задержки настраиваются.
- [ ] Один компактный объект «идущее сейчас» с одним действием; итог 15–30 минут; отписка (D4).
- [ ] Счётчик «ждут вас» в шапке, вкладке, меню-баре (D5); бейдж не единственный канал.
- [ ] Обещано время следующего отчёта, а не завершения (D6).

**Подтверждения**
- [ ] У стадии/блока виден уровень автономии; прерывание доступно всегда (E1).
- [ ] Перед необратимым шагом — превью намерения и критерии успеха/провала (E2).
- [ ] Опрос GO/NO-GO по ролям перед необратимым шагом; любая роль может остановить (E3).
- [ ] Есть мягкое «замечание» и жёсткий «стоп с сохранением» (E4).
- [ ] Вопрос содержит адресата, варианты, предложенный ответ и подтверждение доставки (E5).
- [ ] «Возобновить» показывает, что будет повторено (E6); «откат» показывает, что не откатывается (E7).
- [ ] Собираем свои метрики надзора: доля принятых превью, откатов, эскалаций, время ожидания (E8).

**Стоимость**
- [ ] В шапке: расход/бюджет блока и этапа, темп, окно лимитов провайдера и время сброса (F1).
- [ ] Пороги на факт и на прогноз; у бюджета указан тип «сигнал» или «ограничитель» (F2).
- [ ] Перед запуском команды — диапазон множителя расхода (F3).

**Восстановление**
- [ ] После закрытия окна/перезагрузки состояние возвращается, и видно, что вернулось, что ждёт, что потеряно (G1).
- [ ] Экран возврата: рекап в порядке срочности (G2).
- [ ] Старые «сорвалось» не поднимаются в очередь внимания как свежие; возобновление старого — с подтверждением (G3).
- [ ] У вердикта — ссылка на прогон, роль и основание (G4); «пройдено» выставляет проверка (G5).

**Доступность**
- [ ] Каждое состояние: цвет + форма + слово; отдельная проверка на дальтонизм и монохром (H1).

**Приёмка методом**
- [ ] Наш критерий: на любом экране человек за несколько секунд отвечает на шесть вопросов (см. таблицу выше); проверка — тест на реальных сценариях (чат в папке, планирование по стадиям, ресёрч, команда агентов, ревью, живой прогон, восстановление). Значение «несколько секунд» не из источников — задать в тестовом плане.
